# Changelog v2

Concise release history for `@classytic/arc` v2.

## Unreleased

### Changed — `createOutboxModule` joins the caller's transaction by DEFAULT

`EventOutbox.store()` has always auto-injected a session from `sessionProvider` (an explicit `options.session` still wins). What was missing was the DEFAULT: every host had to remember `sessionProvider: () => transactionContext.get()`, while `auditPlugin` has defaulted exactly that since it shipped.

A host that forgot got no error — it got an event row written outside the transaction, surviving a rollback and reporting something that never happened. That is the guarantee an outbox exists to provide, inverted. This module's own docblock describes two ERP hosts that each had to wire six consumers by hand and each missed one; "remember to pass it" is the same design problem the module was created to end.

Paired with the ambient-session fix above, `outbox.store(event)` inside a `transactional: true` write now commits the event row atomically with the domain write, with no host wiring. New option `sessionProvider?: (() => unknown) | false` — pass `false` for a store whose writes must not join the caller's transaction (separate connection, external queue).

### Fixed — a `transactional: true` write now publishes its session on `transactionContext`

Arc shipped both halves of this seam and never connected them. `auditPlugin` defaults `sessionProvider` to `() => transactionContext.get()` and documents the result as "atomic audit works out of the box" — the audit row committing or rolling back with the domain write. The outbox relay documents the same pattern.

Nothing in arc's request path ever called `transactionContext.run(session, …)`. The default therefore resolved to `undefined` on every request, and those writes went out session-less — OUTSIDE the transaction they were promised to join. A rolled-back domain write left its audit row behind, and nothing surfaced: the request succeeded and the row existed.

`runWritePersistence` now enters the scope with the `TransactionHandle`'s session, so every ambient consumer (audit, outbox, idempotency) joins the transaction as documented. Only when a session actually exists: connection-bound kits (SQLite) pass an empty handle, and entering with `undefined` there would mask an enclosing scope rather than represent this one.

### Changed — `arcLog` resolves per APP, not per process

`configureArcLogger` wrote module-level state and `createApp` called it on every boot, so the last app constructed owned the writer for every app in the process: app A's framework warnings surfaced through app B's transports, level, and redaction. Invisible with one app per process; wrong for multi-app test files and warm serverless containers that reuse a process.

Each app now carries its own options in an `AsyncLocalStorage` scope — entered for the whole boot and, via an `onRequest` hook, for the whole request lifecycle (the same shape `requestContext` uses). All 23 `arcLog()` call sites keep their zero-argument signature.

The process global remains as a documented FALLBACK for arc code running outside any app scope — `defineResource()` at module import, CLI commands, a host calling into arc after `createApp` returns. That fallback is still last-app-wins; anything inside a boot or a request is not. New: `runWithArcLogger(options, fn)` and `enterArcLoggerScope(options, done)` from `@classytic/arc/logger`.

### Fixed — `createTestMcpClient({ auth: null })` ran as an AUTHENTICATED user

`@classytic/arc/mcp/testing` resolved its session default with `options.auth ?? { userId: 'test-user' }`. `??` coalesces `null` as well as `undefined`, so the one value the type documents as anonymous was unreachable: every host test written to prove "an anonymous caller is refused" actually called the tool as `test-user`, and passed while demonstrating the opposite of its name. Only an ABSENT `auth` now takes the default; `auth: null` reaches the tool as a genuine public scope.

Hosts with such a test should re-run it — a previously green anonymous-rejection assertion may have been vacuous.

## 2.34.0 (2026-08-19)

### Added — `nativePolicyFilter()`: an explicit, branded escape hatch for adapter-native policy

repo-core's filter IR is deliberately universal, so semantics only one driver has (MongoDB's `$elemMatch`, for instance) cannot be expressed in it. Server-owned policy sometimes needs exactly those. `nativePolicyFilter(dialect, record)` brands such a filter with a symbol-keyed dialect tag and freezes it, so a policy that bypasses the IR says so in its own value rather than looking like an ordinary filter that happens to work on one kit.

Exported from `@classytic/arc` and `@classytic/arc/core`. **Never apply it to client input** — it is for policy the server constructs.

`mergeFilters` now carries symbol-keyed metadata across a merge. `Object.entries` omits symbols, so a branded native filter silently lost its dialect tag the moment it was conjoined with another policy — the brand survived construction and vanished on first use, which is the worst place for a marker to disappear.

### Changed — client-supplied `_policyFilters` is stripped BEFORE the query parser

Reachable only when a CLIENT puts `?_policyFilters=` in the URL: trusted policy is a request decoration lifted into `metadata` and never enters `req.query`. The old cleanup ran on `parsed.filters` — after `queryParser.parse()` — so on the one path that needed it, it could not run: a kit parser validates every key against `allowedFilterFields` and throws during the parse. Arc's own parser skips the key via `RESERVED_QUERY_PARAMS`, so the two parsers answered the same request differently.

Stripping pre-parse makes kits agree with arc. Note the trade: under a kit parser that probe was a loud 400 and is now silently dropped. The client's value was inert either way — policy is read from `metadata`, never the query.

### Changed — the outbox relay logs its failures by default

`createOutboxModule`'s `onError` defaulted to ABSENT, while its own documentation said "**Wire this.** Silence here is the failure mode that matters: the relay keeps ticking, rows keep failing, and the only symptom is revenue that never posted." A default that logs is strictly better than a default that is silent. Unhandled relay problems now emit a structured `fastify.log.error` (`err`, `kind`, `eventId`, `eventType`). A host-supplied `onError` still wins.

⚠ A deployment that relied on the relay being silent will now see error lines. That is the point — but size it before upgrading.

**Volume.** `onError` fires **per EVENT**, not per batch. With the defaults (`batchSize: 100`, `relayEveryMs: 5000`) a transport outage emits up to 100 lines per tick — roughly **1,200/minute**. Anyone alerting on error-log volume should expect a step change on upgrade, from failures that were always happening and never surfacing.

**And it is UNBOUNDED without a `failurePolicy`.** With no policy, `store.fail()` is called with neither `retryAt` nor `deadLetter`, so a permanently-failing row stays pending and is retried on every poll — forever. The logging does not create that loop; it makes a pre-existing one visible. Two knobs, in order of preference:

- **`failurePolicy`** — the actual fix. Back off and dead-letter after N attempts (`({ attempts }) => attempts >= 5 ? { deadLetter: true } : { retryAt: exponentialBackoff({ attempt: attempts }) }`). This bounds the retry loop AND the logs, and is what the option's own docs already recommend for anything money-shaped.
- **`onError`** — your own handler. Aggregate per batch, sample, route to metrics, or `() => {}` for the previous silence. A host-supplied handler always wins over the default.

### API surface (classified: additive, no narrowing)

- `.` and `./core` **add** `nativePolicyFilter` (runtime + type) and the `NativePolicyFilter` type.
- `./events` and `./integrations/webhooks` report changed declaration CONTENT with no name changes: `OutboxModuleOptions.onError` is now always present on the resolved options rather than conditionally spread, and `DurableWebhookModuleOptions` extends that type so the same edit surfaces there. Widening a call site's guarantee — no exported name removed, no signature narrowed. (The same two subpaths also move when only `onError`'s JSDoc changes: comments ride in the emitted `.d.mts`, so the surface check reports doc edits as content changes.)

## 2.33.0 (2026-08-15)

### Outbox module reports relay failures through Arc's logger by default

`createOutboxModule()` previously left `EventOutbox.onError` undefined unless every host supplied
its own callback before Fastify existed. A failed relay could therefore be counted internally but
produce no structured application log, and hosts reached for `console.error` in composition code.
The module now defaults the callback at bootstrap to `fastify.log.error`, including failure kind,
event id, event type, and the error. An explicit `onError` still wins for metrics or alerting.

### Fixed — a query-borne `_policyFilters` 400'd every list under a kit parser

`QueryResolver.resolve` stripped `_policyFilters` from `parsed.filters`, i.e. AFTER `queryParser.parse()` — a cleanup line that could never execute on the one path that needed it. A KIT parser validates every key against the resource's `allowedFilterFields` and throws during the parse, so control never reached the delete: mongokit answered `400 INVALID_QUERY_INPUT` (`Blocked filter field not in allowlist: _policyFilters`). The strip now happens BEFORE the parse.

Trusted policy never arrives this way — the permission middleware writes the request DECORATION (`request._policyFilters`), which `createRequestContext` lifts into `metadata`, and `req.query` is Fastify's parsed querystring untouched. So the key reaches the parser only when a CLIENT puts it in the URL, or when a host middleware writes the wrong channel (`request.query._policyFilters` instead of `request._policyFilters`) — a mistake arc otherwise absorbs in silence, since the query copy is untrusted and discarded either way.

The two parsers disagreed on that request: arc's own `ArcQueryParser` skips the key via `RESERVED_QUERY_PARAMS` and ignores the probe; a kit's parser rejected it. Stripping pre-parse makes kits agree with arc, and covers mongokit, sqlitekit, pgkit and prismakit at once rather than teaching each kit's reserved-key list about an arc-internal name.

The trade, stated so it is not rediscovered as a regression: a client-supplied `?_policyFilters=` is now silently dropped rather than rejected. Policy itself is unaffected — it is read from `metadata` and conjoined as before, and a test asserts it survives into the outgoing filter. `req.query` is copied, never mutated, and only when the key is present.

### Write verbs — bind a CRUD slot to a domain command without losing the pipeline

`defineResource({ writes: { create?, update?, delete? } })`. Arc runs its whole request pipeline — body sanitization against field rules, tenant injection, `createdBy`/`updatedBy` stamping, the before/around/after hook sandwich — then calls YOUR command where it would have called `repository.<op>`. Closes the two-way trap where a resource with a kernel-guarded write (`updateDraft()` that refuses once posted) had to choose between the guard and the pipeline, losing the other silently: measured live, an override added to close the first hole let `PATCH` write `status: "posted"` and a forged `number` through 8 declared `systemManaged` fields, answering 200.

- **Verbs receive the repository PRIMARY KEY** (`resolveMutationRepoId` output), never the raw route param — a resource with `idField: 'slug'` routes on the slug while its repository keys off `_id`, and a command handed the slug targets nothing. `ctx.req.params.id` still carries the route value.
- **Contexts are per-op and honest**: `WriteContext` (create) and `MutationWriteContext` (update/delete — `id` + `existing` REQUIRED, because `loadMutableTarget` throws before any verb when it cannot produce the target). `ctx.repository` is typed `RepositoryLike<TDoc>`, not `unknown`.
- **Return contract**: a command signals failure by THROWING. `create` must return the created document — a nullish return throws `WRITE_VERB_CONTRACT_VIOLATION` (500) instead of answering a hollow 201 with after-hooks fed a non-document. `update` may return `void` (arc re-reads once to answer; returning the doc avoids the read). `delete` returning `void` is success, never a 404.
- **Reachability is boot-fatal, not advisory.** A declared command that can never run is the same defect one layer up, so registration THROWS when: the controller is not built on arc's write pipeline (capability is a prototype mark on `BaseCrudController`, `Symbol.for`-keyed so it survives duplicated arc copies — a duck-typed `configure()` is NOT proof); or the declared verb's CRUD method is OVERRIDDEN (route dispatch calls the override; the verb behind it is dead code — measured `verbCalled: 0`; wrap behaviour with `hooks` instead, including delegating overrides, whose reachability is statically unprovable). Malformed declarations are config-validation ERRORS: unknown slots (`writes.patch`), non-function entries (`update: "updateDraft"`, `update: undefined`) — arc is a JS runtime framework and a malformed entry degrading into generic CRUD is a security regression.
- Override detection is ONE implementation (`detectOverriddenWriteSlots`): own-property provenance marks catch class-field overrides (arc's constructor binds all three write methods, so `Object.hasOwn` alone says nothing), a chain walk to the capability-marked prototype catches subclass prototype methods.
- Warn (unchanged in spirit, now shared-detection): a write-verb-capable controller overriding `create`/`update` while the resource declares field protection, with no verb declared for the slot.
- New exported types: `ResourceWrites`, `WriteContext`, `MutationWriteContext`, `WriteVerbKey` (root + `/types`).
- Covered by 40 tests including HTTP round-trips (`app.inject`) proving which side of the seam ran, and mutation-tested (each enforcement removed → the intended tests fail).

### Transactional write envelope — `defineResource({ transactional: true })`

Every CRUD write (repository call or declared verb) runs inside the repository's transaction with TRANSIENT-conflict retry: begin → persistence → commit, re-run only on kit-classified conflicts (repo-core `retryingTransaction`, jittered bounded backoff), everything else surfaces once — including `VersionConflictError`, which a CAS loser must answer by re-reading, never re-running. The persistence step receives the TX-BOUND repository — declared verbs get it as `ctx.repository`, so a kernel command composing with the repo joins the same transaction — and `ctx.uow` carries the repo-core `TransactionHandle`: `outbox.store(event, { session: ctx.uow.session })` commits the event row atomically with the business write (connection-bound backends pass an empty handle; their tx-bound repo is the only join point). Absent without the flag — no phantom transaction implied.

Contract, and the tests pin each clause: before/around hooks run ONCE (outside the retry — their side effects must not repeat); after-hooks run once, post-commit; the flag on a repository without `withTransaction` is **boot-fatal** (a requested envelope that silently degrades to bare writes is the defect, not a mode); without the flag, nothing changes.

**⚠ Peer floors:** `@classytic/repo-core` `>=0.17.0` → `>=0.24.0` and `@classytic/primitives` → `>=0.23.0`. Both imports are static, so an older peer fails at module load rather than degrading. repo-core moved twice: `>=0.23.0` for `retryingTransaction` + the conflict taxonomy + `asReadOnlyRepo`, then `>=0.24.0` for `disposition` on `CleanupStep` / `CleanupStepEstimate`, which the cleanup module reads. primitives `>=0.23.0` is the outbox FENCING contract — published 0.22.0 does not contain it.

### Framework default sort withdraws when the parser forbids it

`QueryResolver` applied arc's own `-createdAt` default on resources whose `allowedSortFields` omitted `createdAt`; mongokit ≥3.25 rejects blocked sorts, so every list call 400'd with no request a caller could make to avoid it (REST and MCP alike). The FRAMEWORK default now withdraws when the allowlist forbids it (`permittedDefaultSort`); a HOST-declared `defaultSort` is left alone — a contradiction the author wrote is theirs to resolve. Pairs with mongokit 3.32.0, which stopped rejecting its own parser-level default.

### Single-node topology is declarable — the memory transport as a supported configuration

One process is a legitimate production topology (one VPS, on-prem, no Redis budget): with no other instances to broadcast to, the memory transport is exactly sufficient. `eventPlugin, { singleProcess: true }` — or an EXPLICIT `createApp({ runtime: 'memory' })`, which flows down automatically — downgrades the every-boot memory-transport warn to an info line stating the real semantics. Undeclared memory keeps the warn — it is indistinguishable from a multi-replica app that forgot to configure a transport — and declaring the flag alongside a cross-instance transport warns about the contradiction.

### `MemoryEventTransport({ onHandlerError: 'throw' })` — at-least-once PROCESSING on a single node

The single-node durable composition (repository-backed outbox → memory transport) guaranteed at-least-once **publication**, not processing, and nothing said so. With this transport `publish()` IS the handling — subscribers run synchronously, in-process — so a swallowed handler error read to the relay as a successful delivery: measured, a handler throwing once produced `relayed: 1, publishFailed: 0` and the next tick found nothing to retry. The durability the outbox bought stopped at the publish call.

`onHandlerError: 'throw'` makes `publish()` REJECT with an `AggregateError` after running every matching handler, so the relay leaves the row unacknowledged and `failurePolicy` retries or dead-letters it. Default stays `'log'` (unchanged fire-and-forget semantics — one broken analytics subscriber must not fail a publisher's request). Retry redelivers to ALL matching handlers, so handlers must be idempotent; a failing handler never aborts the others. A broker-backed transport has no such ambiguity — publish means "durably handed off" and redelivery is the consumer group's job. [[delivery-guarantees]] now carries the two-column table.

### The outbox relay published NOTHING through its default transport

`createOutboxModule` defaulted its transport to `fastify.events` via an `as EventTransport` cast across two INCOMPATIBLE shapes. The decorator is a request-facing facade taking `publish(type, payload, meta?)`; the relay calls `publish(event)`, so the `DomainEvent` envelope arrived as the `type` argument and failed the non-empty-string guard. Measured on the documented default wiring: subscribers received `[]`, every tick reported `publishFailed: 1`, and rows retried until dead-lettered. The cast is what let the mismatch typecheck; the only existing coverage asserted that `bootstrap()` did not throw, which it never did.

Fixing the shape alone would not have been enough — the facade is FAIL-OPEN (`if (!failOpen) throw`), so a handler failure would be swallowed and the row acknowledged, reintroducing one layer up the exact defect `onHandlerError` closes. The boundary is now explicit: **the HTTP-facing facade may fail open; the relay must observe failure.** The plugin decorates the raw transport under `ARC_EVENT_TRANSPORT` (a `Symbol.for` key, off the public `EventsDecorator` surface) and the module resolves that.

A module that cannot resolve a transport now REFUSES TO BOOT. Previously `EventOutbox.relayBatch()` returned an empty result when it had none, so the schedule ticked forever, published nothing, and let the store grow while reporting healthy — the same silent failure reached from the other side.

Covered by an integrated suite that composes the real thing (plugin + default module wiring + a subscriber failing once): the relay reports the failure, retains the row, retries it, acknowledges on success, and finds no pending work on the third tick.

### Outbox relay identity is unique per RELAY INSTANCE

`createOutboxModule`'s default `consumerId` was the shared literal `'arc-outbox-relay'` — run two replicas without setting it and every process is the same logical lease owner, so a lease that expires and is re-claimed elsewhere passes the ownership check as if it never moved (stale-owner protection pinned open). Now `<name>:<hostname>:<pid>:<random>`, minted per relay instance at bootstrap and stable across that relay's ticks.

Per INSTANCE, not per process: a lease identifies an independently executing claimant, and arc lets two outbox modules coexist, each with its own schedule arm and nothing stopping both from pointing at the same store. Scoping it per-process would also have made the module weaker than the primitive it wraps — `EventOutbox`'s own fallback is already per-instance. The module name makes a lease row say WHICH relay holds it; the random suffix breaks the tie a container restart creates (same hostname, often the same pid). An explicit `consumerId` still wins and must stay distinct per relay.

### Published `/testing` types no longer name a package arc does not depend on

`createMockController`'s return type was INFERRED, and inference expands `Mock`'s default type argument to `Procedure` — declared in a vitest-internal sub-package arc has never listed. The emitted `.d.mts` referenced that package by name: resolvable under npm's hoisting (the real `vitest` peer drags it in), broken under pnpm's strict layout, where a transitive dependency is not reachable from a consumer's root. Any host importing `@classytic/arc/testing` types on pnpm could fail to resolve them.

The return type is now written out with bare `Mock`, which IS `Mock<Procedure>` — the same type for every consumer, naming only `vitest`. Emission-only: no widening, no narrowing, no signature change. Pre-existing since at least 2.32.0; knip's unlisted-dependency finding is now clean.

### Outbox fencing tokens — `repositoryAsOutboxStore` (every kit, one implementation)

`claimPendingFenced` on the generic adapter (primitives contract): the fencing token rides the SAME CAS that claims the row — `inc: { fenceToken: 1 }` beside the attempts bump — so a takeover after lease expiry mints a strictly greater token in the very statement that takes ownership; no second round trip, no window. `acknowledge`/`fail` accept `fencingToken` and add it to the CAS guard filter; a stale epoch throws `OutboxOwnershipError` even when the consumerId matches (holder ids recur; epochs do not — the overlap ownership checks narrow but cannot close). `claimPending` delegates to the fenced path: one claim implementation. Requires primitives with the fenced contract; feature-detected end to end.

**The relay closes the loop:** `EventOutbox` prefers `claimPendingFenced` when the store offers it, keeps each event's token, and hands it back on BOTH exits — `acknowledge` and `fail` — so a relay that lost its lease mid-batch cannot ack (or re-schedule) a row a successor already owns. Stores without the fenced claim are untouched: plain `claimPending`, then `getPending`, exactly as before.

### `ArcModule.plugins` is a setup function, and the misuse its name invites now fails loudly

The slot is CALLED by arc — never handed to `fastify.register()` — so there is no encapsulation and no prefix, and a module must register its own plugins. Nothing said so, and the type signature cannot distinguish the mistake: returning a plugin (expecting arc to register it) was read as the disposer shorthand, so it registered NOTHING at boot and then invoked the plugin at shutdown with no arguments.

Now detected at the point of return: a `fastify-plugin` throws (its marker symbols are set only by `fp()`, so there are no false positives), and a multi-argument function warns (arc calls disposers with zero arguments, so a 2-parameter disposer is meaningless either way). The JSDoc states the encapsulation consequence up front. `setup` is the v3 rename, and v3 removes `plugins` outright — v3 ships no compatibility aliases (see v3.md).

### The ungated-CRUD warning names the switch that fixes it

`strictPermissions` / `ARC_STRICT_PERMISSIONS=true` turns an ungated WRITE from a warning into a boot failure, but the warning never mentioned it — a host reading "state intent explicitly" had no way to know the whole class of mistake could be made impossible. The warn now names it as the production posture and flags it as the v3 default. Behaviour is unchanged; this is text at the point of decision.

### Dev-tree on latest majors; CI's floor lane no longer tests fiction

The test tree moves to `bullmq` 6, `ioredis` 6, `fastify-raw-body` 6, `better-sqlite3` 13, `fastify` 5.12, and the latest kits — 6793 tests green. **Peer floors are UNCHANGED** (`>=5.0.0` for the three optional peers): the suite passed on both the v5 and v6 majors, so `>=5` is a truthful claim and raising it would break hosts for no reason. `@types/node` deliberately stays on 22 to match `engines: node >=22` — typing against a newer runtime lets source reach APIs the minimum does not have.

**The `peer-minimums` CI lane derives its pins from `package.json` instead of hardcoding them.** It still read `repo-core@0.14.0` / `primitives@0.9.0` while the declared floors had moved to 0.24 / 0.23 — so the job whose entire purpose is proving the floors are real had been installing versions arc can no longer build against. Reading the manifest means raising a floor automatically changes what CI installs, and a floor arc cannot build against fails on the PR that raised it rather than months later. Verified locally at the real floors (fastify 5.8.5 + repo-core 0.24.0 + primitives 0.23.0): typecheck, build, and the contract/type lanes all pass.

### MCP carries the same scope dimensions as HTTP

`buildScope` built MCP's `RequestScope` without `teamId` or `context`, even though a resolver could already return them (`McpAuthResult` has an index signature). A resource gated by `requireScopeContext('branchId')` therefore worked over HTTP and DENIED every MCP call — the dimension it authorises against was never populated. It failed CLOSED, which is exactly why it went unnoticed: the tool was unusable rather than wrong, and an unusable tool reads as a permissions problem.

Both are now carried — `context` onto `member` and `service` scopes, `teamId` onto `member` only, matching the HTTP surface. Both are declared explicitly on `McpAuthResult` rather than left to the index signature, because a field you must supply for authorisation to work should be discoverable in the type. A resolver's `context` is accepted only as string→string: non-string entries are dropped rather than coerced, since a coerced value would have `requireScopeContext` comparing against something that was never a branch id, and an empty result yields no context rather than an empty one.

### Scope projection carries `teamId` + `context` — and the context is frozen

`RequestScopeProjection` (what hooks and write verbs receive as `ctx.scope`) gained two optional fields, so host code reaches team and custom dimensions through the projection instead of reaching into the `RequestScope` union — the same rule the `getUserId`/`getOrgId` accessors exist to enforce. Additive in both directions: readers see more, and the fields are optional so anything constructing a projection still satisfies the type.

**The `context` map is now a FROZEN COPY, not the live one.** `Readonly<Record<string, string>>` is erased at runtime, so the annotation protected nothing — the projection handed out the scope's own object and `ctx.scope.context.branchId = 'other'` in a hook rewrote the caller's real scope. `requireScopeContext()` authorises against exactly those dimensions, so a later permission check in the same request would read the tampered value and allow what it should refuse. A copy rather than freezing in place: the map belongs to whoever built the scope, and freezing someone else's object as a side effect of reading it is a surprise a library should not spring. ESM is strict mode, so a write now throws where it is made.

Note the annotation is still advisory for direct `getScopeContextMap(scope)` callers — that accessor returns the live map. The projection is the surface host extension code actually receives, and that is what is sealed.

### API-surface note (classified: additive, no narrowing)

Nine subpaths report changed declaration CONTENT with no name changes. Both causes are additive:

- `WriteContext.uow` / `runWritePersistence` / `writeContext` / `mutationWriteContext` now reference repo-core's imported `TransactionHandle` instead of an inline `{ session?: unknown }`. `RepositorySession` is `unknown`, so the structural type is IDENTICAL — this is an alias swap, not a narrowing. It does mean arc's emitted `.d.mts` imports the name from `@classytic/repo-core/repository`, which is why the peer floor moves to >=0.23.0 (the type was previously defined there but not re-exported).
- `RepoCapabilities` gains optional `transactionRetry` and `readOnly`, which flow into every arc subpath that references the descriptor. Optional additions; absent keys keep their prior meaning.

No exported name was removed, and no signature narrowed.

### CLI — flags that were advertised but unwired, and `arc <cmd> --help`

`bin/arc.js` is the only unbundled, untyped file arc ships, so nothing checked that the flags it documents are the flags it parses. Three defects, all found by adding that check:

- **`--api-key` and `--session` did nothing.** Both were advertised in `arc init --help`, declared on `InitOptions`, and prompted for interactively — but `parseInitOptions` had no case for either. A scripted `arc init --better-auth --api-key --skip-install` printed "unknown flag (ignored)" to stderr and scaffolded a project WITHOUT the plugin. Non-interactive is exactly where nobody reads the warning. Now parsed, with `--no-api-key` to decline without being prompted.
- **`arc <command> --help` printed the global manual.** The top-level help check scanned all of argv, so it fired before routing and the per-command usage in `COMMAND_HELP` was unreachable dead code. Global `--help` / `--version` are now the LEADING argument only.
- **`--name` was parsed but undocumented.**

**`process.exitCode` replaces `process.exit()` throughout.** `process.exit()` tears the process down immediately, and on POSIX a stdout that is a pipe writes asynchronously — so an exit racing the flush truncates output (`arc describe --json > out.json`, `arc --help | less`). Arc's own `doctor` already set `exitCode`; this file was the exception. Every exit code is unchanged: misuse is 1, success 0.

A `tests/cli/bin-flag-contract.test.ts` suite now pins both directions — every advertised flag is parsed, every parsed flag is advertised — plus the exit-code contract and the no-`process.exit()` rule.

### Fixed — arc closed stores and transports it did not own

`onClose` called `close()` on the idempotency store, the events transport, and the query-cache store unconditionally — including when the HOST supplied them. A host-supplied resource may be shared with another app in the same process (a documented topology, and what every integration suite does) or simply outlive the app. `MemoryIdempotencyStore.close()` CLEARS its maps, so shutting down the first app wiped the second app's live idempotency records: replayable requests silently became re-executable. For a Redis-backed transport the same call severs a connection arc never opened.

Arc now closes only what arc BUILT. A store or transport handed in from outside is the host's to close; the arc-built defaults are still closed, so nothing leaks (the memory store's cleanup interval in particular).

### Fixed — the idempotency boot self-check could fail a rolling deploy

The self-check's cleanup swept the entire `__arc_idempotency_selfcheck__:` prefix rather than its own probe keys, for self-healing. With several replicas booting against one shared store — the normal rolling-deploy shape — one replica's cleanup deletes another's IN-FLIGHT probe, and that replica then reports "a written probe entry did not read back under its own key" and refuses to boot. A guard that takes down the deployment it protects, intermittently, at deploy time. The sweep is now scoped to this boot's probe suffix. Self-healing is not lost in any way that matters: probes carry a 60s TTL and `get` already filters expired entries, so residue from an interrupted boot ages out on its own.

### ⚠ Repository capability gates: read the descriptor, not the method table

Two boot gates were method-presence checks, and both were bypassable by the exact deployments their own error messages named.

**`transactional: true` now checks `capabilities.transactions`** — kits expose `withTransaction` unconditionally and fail at BEGIN, so a standalone-Mongo deployment booted clean and 500'd on the first write. Split across two lifecycle points, because they settle at different times: a MISSING `withTransaction` throws at `defineResource()` (knowable immediately), while the deployment's capability is asserted at REGISTRATION (lifecycle slot 5). `defineResource()` usually runs at module import, before `beforeBoot()` connects, and a kit reports `transactions: false` for an unresolved topology by design — asserting early would reject a correctly configured app for importing its resources eagerly. At registration, anything other than a confirmed `true` fails the boot. Repositories with no descriptor (hand-written, custom kits) keep the presence check alone.

**Write routes over a READ-ONLY repository are refused at boot.** `capabilities.readOnly` (repo-core) marks a repository whose rows another component owns and whose invariants generic CRUD would bypass — Better Auth hashes passwords, revokes sessions, and cascades org membership on every write it performs. Both kits' Better Auth overlays now seal their repositories by default, so the runtime write throws; this gate turns that into boot-time feedback naming the routes and both ways out (`disabledRoutes`, or the kit's `unsafeWritable: true`).

**Arc no longer stacks a retry policy on a self-retrying kit.** `retryingTransaction` reads `capabilities.transactionRetry`: mongokit declares `'managed'` (its driver re-runs the callback internally for up to 120s) and is invoked exactly once; sqlitekit declares `'caller'` and gets the envelope's loop. Previously arc wrapped every kit in 5 attempts regardless — with MongoDB that made the callback's execution count unbounded, `onRetry` telemetry partial, and each outer attempt a fresh session. Requires repo-core >=0.23.0.

**`WriteContext.uow` is repo-core's canonical `TransactionHandle`**, imported rather than restated as `{ session?: unknown }` — a field added to the contract now reaches write verbs instead of being dropped at arc's boundary. (repo-core 0.23.0 exports the type; it was previously defined but not re-exported, which is why the restatement existed.)

### Durable webhook delivery — composition, not a second queue

`webhookPlugin({ durable: { store } })` + `createDurableWebhookModule({ store })`. Inline dispatch's `retry` lives in the process, so a crash or deploy silently drops the remaining attempts — the documented gap ("guaranteed delivery is a durable-job concern") is now closed with the machinery arc already has rather than a parallel delivery queue.

A webhook delivery IS an outbox event. The plugin writes one row per (event × subscription) instead of POSTing; `createDurableWebhookModule` wraps `createOutboxModule` with a publish-only transport whose `publish()` performs the signed POST — so lease, claim, **fencing**, failure policy, DLQ, and the `kind: 'relay'` schedule arm all apply unchanged, and `role: 'api'` enqueues while `role: 'relay'` delivers.

- **Enqueue is exactly-once per (event, subscription)** even behind an at-least-once transport: the row id is deterministic (`<event id>:wh:<subscription id>`) and doubles as `dedupeKey` — repository stores swallow the dup-key, the memory store dedups on the key.
- **Wire contract unchanged.** v1 signing; `x-arc-webhook-delivery` carries the ORIGINAL event's `meta.id`, so receiver-side dedup is identical to inline.
- **Failure classification drives the policy, not the attempt count alone.** `WebhookDeliveryError` marks network/timeout/429/5xx transient; 4xx, a 3xx under `redirect: "manual"`, a URL-policy rejection, and a malformed row are permanent and dead-letter on the FIRST attempt — a rejected payload cannot succeed by repetition, and a wiring bug must not retry for hours. `webhookDeliveryFailurePolicy` (default: 8 attempts, 5s base, 15min cap) is replaceable.
- **URL policy is enforced at DELIVERY time too**, covering rows enqueued before a policy existed and out-of-band store writes.
- Boot-fatal: `durable` + `retry` together (two retry axes on one delivery), and a delivery module without `webhookPlugin` (subscriptions resolve through `fastify.webhooks`).

### Runtime capability registry — the checklist becomes enforcement

`declareRuntimeCapability(fastify, { subsystem, durability, accepted?, detail? })` (`@classytic/arc/utils`): subsystems holding process-local state declare it at registration — arc's own plugins AND host `plugins()` callbacks, which is the point: `validateDistributedRuntime` can only inspect what `createApp` receives, so host-wired stores lived on a wiki checklist, and a checklist is not enforcement. One audit at the END of boot fails a `runtime: 'distributed'` app on every undeclared-shared memory capability, ALL violators named in one error; `accepted: true` marks per-process-by-design state (logged, never fatal). The webhooks plugin declares its default in-memory store. The early guard keeps its fast-fail job for constructor-visible stores — one policy, two collection points, one enforcement.

### `createApp({ role })` — declared topology

A process states its deployment role and refuses contradicting work. `'api'`/`'worker'` mount NO module schedule arms (the outbox relay arm included — a worker/API fleet must not compete with the relay deployment); `'relay'` mounts ONLY `kind: 'relay'` arms (`ScheduleDefinition.kind`, new; the outbox module tags its arm); `'scheduler'` mounts everything; `'all'` (default) changes nothing. Skipped arms are logged BY NAME at boot. `role: 'relay' | 'scheduler'` with HTTP `resources`/`resourceDir` is boot-fatal — those roles exist to not serve traffic, and mounting routes anyway would hide the misdeployment behind a working endpoint. Pair with `jobsPlugin({ mode })` below. `createWorker` forwards `role` untouched — ONE topology axis, not two mechanisms; its default stays `'all'` (its 2.23 headless-runs-everything contract, so nothing existing changes), and `role: 'worker'` there drops the arms when a dedicated scheduler/relay deployment owns them.

### `jobsPlugin({ mode })` — producer/worker split (topology plan, Phase 2 first slice)

`'producer'` constructs queues only: `dispatch()` works, NO Worker is built, and repeat-schedule reconciliation is not owned (a producer cannot execute what it schedules, and its stale-scheduler sweep would fight the worker fleet's). `'worker'` builds queues + workers; `'both'` stays the default — single-process behaviour unchanged. Before this, every API replica that registered the plugin competed on every queue, so handler concurrency scaled with HTTP fleet size — backwards.

### MCP smoke restored to the release gate

`scripts/mcp-e2e.mjs` had been dying at module resolution since 2.12 (importing the deleted `dist/adapters/`) without exercising an assertion; fixed (kit adapter import, `.data` envelope) and wired into `prepublishOnly` as `smoke:mcp` so it cannot silently rot again. mongokit devDep `^3.32.0`.

### Docs

`wiki/delivery-guarantees.md`: new composition rules — **automatic CRUD events ≠ transactional outbox events** (auto-emission publishes AFTER the write, outside any transaction, fire-and-forget; a durable guarantee requires the domain command to write the outbox row in the SAME session), per-relay-instance identity, and the facade-vs-relay boundary — plus a "Single-node deployment (no Redis)" section with the publication-vs-processing table.

### Silent input drop — two paths where arc widened instead of failing

Both observed live against a running deployment, both HTTP 200, neither logged.

**1. An unknown filter key was DROPPED, and dropping a filter WIDENS.** The caller asks to narrow; the whitelist rejects the key; the query runs unfiltered and answers `200`:

```
?filters[status]=pending&filters[flow]=inflow  → 200, 10 rows, every one status:"verified"
?status=pending&flow=inflow                    → 200, 0 rows
```

The same shape had already cost weeks elsewhere: `?productId=…` where the param is `skuRef` returned a *different product's* 75 units, filed as "quant leakage".

New `ArcQueryParserOptions.strictFilterFields` (default `false`, env `ARC_STRICT_QUERY_PARAMS=true`) throws `ValidationError` naming the key and the allowed set. Off by default because arc is published and an unconditional throw would reject requests that work today; hosts opt in from their env-loader, mirroring `ARC_STRICT_PERMISSIONS`. Resolution is `??` so an explicit `false` beats the env — a general default must never override a specific one. **Only the filter whitelist is covered**: a dropped sort or operator degrades ordering, it does not widen the row set.

**2. A write to an `immutable` field was STRIPPED and reported as success.** `PATCH {"type":"rent"}` returned `200` with `"type":"purchase"` unchanged — a UI offering that field reports success and changes nothing.

New `BodySanitizerConfig.onImmutableWrite` (default `'strip'`, env `ARC_STRICT_IMMUTABLE_WRITES=true`) throws `ForbiddenError` listing the fields. **Deliberately NOT folded into `onFieldWriteDenied`**, which defaults to `'reject'`: a full-object PATCH echoing an immutable field back *unchanged* is legitimate, and the sanitizer has no stored document to tell it from a real change — sharing that default would break those callers. This closes an inconsistency inside arc, which had already decided a denied write should surface as a 403 rather than a silent no-op; `immutable`/`readonly`/`systemManaged` simply never routed through that policy.

Pinned by `tests/security/silent-input-drop.test.ts` — characterisation tests for the old behaviour alongside the new, so the drop cannot return unnoticed. Both guards falsified by removal (each fails only its own assertion) and restored; full suite 6571 passing.

## 2.31.0 (2026-07-29)

### ⚠ Breaking: `RouteDefinition.raw` removed — the FIELD carries the intent

A custom route used to declare one `handler` and a `raw: boolean` beside it saying how to call it. Both mismatches were legal:

```ts
// Fastify-shaped function, no flag → silently run through the arc pipeline,
// so `reply` is arc's, the return value is enveloped, and the response is wrong.
{ method: 'GET', path: '/report', handler: async (req, reply) => reply.send(buf), permissions }

// Pipeline handler WITH the flag → invoked as (request, reply); `ctx.params`
// resolves off a FastifyRequest by luck and `ctx.repository` is undefined.
{ method: 'GET', path: '/stats', raw: true, handler: async (ctx) => ({ data: … }), permissions }
```

Neither was a type error, because one field held every shape. The flag is gone; the field you fill IS the declaration:

| Field | Signature | Behaviour |
|---|---|---|
| `handler` | `(ctx: IRequestContext)` **or** a controller-method name | Arc pipeline — envelope shaping, field-write permissions, MCP tool by default |
| `rawHandler` | `(request, reply)` **or** a controller-method name | Fastify-native — owns the response, no pipeline, no MCP unless `mcpHandler` is set |
| `controllerMethod` | `(c: MyController) => c.method` | Typed pipeline ref — TS catches typos |

Declaring both throws at boot. `streamResponse: true` now REQUIRES `rawHandler` — it invokes the handler with `(request, reply)` and hands it the socket, so a pipeline `handler` there could never stream.

**Migration** is mechanical: delete `raw: true` and rename that route's `handler` to `rawHandler`; delete a bare `raw: false` (it was the default). Both fields accept a controller-method NAME, so string handlers keep working either way.

**A leftover `raw` is FATAL at boot, not ignored.** Silently dropping it would pipeline-wrap a Fastify-native handler — the exact failure the split exists to remove — and `tsc` only sees the flag in sources recompiled against 2.31, *not* in a dependency whose published dist still emits `raw: true`. So arc throws, naming the route and pointing at the package. **⚠ Every `@classytic/arc-*` package must be rebuilt against 2.31**; until then a host that depends on one will fail to boot rather than 500 at request time.

`streamResponse: true` now **requires** `rawHandler`, stated as a positive invariant rather than "rejects `handler`": the router derives raw-ness from `rawHandler` alone, so a `controllerMethod` route would otherwise validate, be pipeline-wrapped, and *then* be handed to the streaming wrapper as a third execution model nobody declared. Relatedly, the streaming wrapper invokes the inner handler with `.call(this, …)` — Fastify binds the instance as `this` when it dispatches a handler, and dropping it meant the same handler could read `this.myDecorator` fine as a plain raw route and break the moment `streamResponse` was switched on.

`controllerMethod` is now typed **pipeline-only** (`(controller) => ControllerHandler`). Its docs previously promised it could return a raw Fastify handler "when the route uses `rawHandler`" — impossible, since the two fields are mutually exclusive. For a Fastify-native controller method, put its NAME in `rawHandler`.

Two gates keep this from rotting. `scripts/check-removed-route-api.mjs` (wired into `prepublishOnly` as `check:route-api`) fails on the removed flag anywhere in `src/`, `docs/`, `skills/`, `wiki/`, `examples/` or `tests/` — release notes are allowlisted. It exists because the drift lives exactly where tsc and biome don't look: **`arc init` kept emitting `raw: true` through a green typecheck and a green scaffold suite**, since CLI templates are backtick STRINGS (the compiler checks the template, never the app it emits) and the suite only asserted that generated files exist. Seven generated auth routes were affected; the scaffold suite now asserts the generated resource uses `rawHandler`.

This also fixes inference. `handler` previously carried `string | ControllerHandler | RouteHandlerMethod | ((request: never, reply: never) => unknown)`; TypeScript contextually types a parameter only when exactly ONE constituent is callable, so an inline `handler: async (req, reply) => …` reported TS7006 and every author annotated by hand. `rawHandler` is one function type (`RawRouteHandler`, now exported), declared with method syntax so its parameters stay bivariant — `FastifyRequest<{ Body: CreateBody }>` assigns with no cast, which is what the old `never`-parameter member existed to allow. Fastify types its own `RouteOptions.handler` as a single type for the same reason.

### DB-agnostic boundary is now machine-enforced

"No DB driver imports anywhere in arc" was a documented rule with no gate — the state a rule rots in, since one `import mongoose` in a helper makes the driver a hard dependency of every non-Mongo host. `scripts/check-boundaries.mjs` (already gating layers and cycles, and run by `prepublishOnly`) grew a third check over drivers and storage kits: `mongoose`, `mongodb`, `pg`/`mysql`/`better-sqlite3`, `drizzle-orm`, `@prisma/client`, `typeorm`/`sequelize`/`knex`/`kysely`, and every `@classytic/*kit`.

The distinction it draws is static vs dynamic, because that is the distinction that reaches a consumer: a top-level import is unconditional, while an `await import()` behind an injectable port costs nothing until called. Static imports always fail; the two lazy ones (`testing/bootModuleApp.ts`, `testing/testApp.ts` — the default in-memory Mongo test database, overridable) are allowlisted with a reason, and the gate reports an allowance that stops being needed. CLI template directories are skipped: `arc init` writing `import mongoose` into a scaffolded app is arc writing an app, not arc importing a driver.

No source change was required — arc's runtime dependencies remain `fastify-plugin`, `qs`, and `secure-json-parse`.

### Optional and deferred sibling-module reads (`@classytic/arc/factory`)

`getModuleExports` throws — correct for a required, already-bootstrapped dependency, and the wrong shape for the two reads hosts actually had. So every host hand-rolled them:

```ts
(fastify as unknown as { arc?: { modules?: Record<string, unknown> } }).arc?.modules?.inventory
```

A double cast that defeats `ArcModuleRegistry` inference, survives a typo in the module name, and cannot be grepped for. Four additive accessors replace it:

| New | Use when |
|---|---|
| `getOptionalModuleExports(f, name)` | the module is genuinely OPTIONAL — `undefined`, no throw, no cast |
| `hasModuleExports(f, name)` | a readiness predicate (`ready: () => …`) |
| `lazyModuleExports(f, name)` | the read is WIRED at composition time and USED later; optional |
| `lazyRequiredModuleExports(f, name)` | same, but a hard dependency — the fail-fast throw moves to first use |

The lazy pair exists because wiring is often *registered* earlier than it *runs* (an `eventHandlers` factory, a bridge accessor handed to another module, a hook added at bootstrap and fired per request). Such a factory can execute before the sibling it needs has bootstrapped, so a sibling engine captured into a local at that moment is `undefined` — and stays `undefined` for the process lifetime even though the sibling came up milliseconds later. That failure is **silent by construction**: the consumer reads a null bridge as "this deployment has no inventory / no revenue engine", a legitimate configuration. Observed cost downstream: orders created and never payment-confirmed (no entitlement, no card, no door), with nothing erroring anywhere.

The lazy getter therefore re-reads while the module is absent, memoizes the first resolved value, and **never memoizes absence**.

```ts
const inventory = lazyModuleExports<FlowEngine>(fastify, "inventory");
return {
  flowBridge: () =>
    inventory() ? createFlowEngineBridge({ getFlowEngine: () => inventory()! }) : null,
  ready: () => inventory() !== undefined, // drawer-only deployment: legitimately false
};
```

### ⚠ Job management endpoints are no longer public

`GET /jobs/stats` and `GET /jobs/:id/status` were registered with no authentication and no permission check. A status carries `returnValue` and `failedReason` — the handler's own output and error text, which routinely hold export URLs, billing results, model output, recipient addresses, or internal stack detail. Unauthenticated, a job id was a read primitive over other tenants' work.

The surface is now **off by default**, and the permission is mandatory — no shape of the option yields an unguarded route:

```ts
jobsPlugin({ managementRoutes: { operatorPermission: requirePlatformRole("platform-ops") } })
```

Arc **verifies** that at boot rather than trusting the name: the gate must carry `_platformOnly` — new `requirePlatformRole()`, which consults platform roles alone. That check exists because the property is unprovable per-request: `requireOrgRole("manager")` grants ANY org's manager, and `requireRoles(["platform-ops"])` is satisfied by an ORG role of that name (its documented default), yet both return a bare allow with **no policy**. A custom check can opt out with `allowUnverifiedOperatorPermission`.

It is named `operatorPermission` because it is a **platform surface, not a tenant-facing one**. A BullMQ job carries no framework-level tenant identity and `getStatus` fetches straight by queue + id, so a row-level `policy` on the decision has nothing to filter — `requireOrgRole("manager")` would let a manager in org A read a known handle from org B, and `/stats` is inherently global. Arc therefore **refuses** a request whose decision carries a `policy` (`403 arc.jobs.policy_unsupported`, logged) rather than accepting it and silently ignoring it: arc's semantics say a policy is enforced, so the honest choices are refuse or mislead. Serve tenant-facing job status from a resource that owns its own row policy.

`returnValue` and `failedReason` are redacted unless `exposeResult` / `exposeFailureReason` are set, so enabling the surface does not implicitly publish handler output. Queue-level counts remain available through the metrics/health integration, which never exposes individual jobs.

### ⚠ Job status is queue-qualified; `dispatch` returns a `JobHandle`

BullMQ ids are **queue-local**, so `getStatus(jobId)` had to scan every registered queue and returned whichever matched first — ambiguous when two queues hold the same id, and one Redis round trip per job type on every request.

```ts
const { queue, jobId } = await fastify.jobs.dispatch("email", data);  // was { jobId }
await fastify.jobs.getStatus(queue, jobId);                            // was getStatus(jobId)
// GET /jobs/:queue/:id/status                                          // was /jobs/:id/status
```

### Duplicate job names and invalid numeric options fail at boot

A duplicate name silently created two queues and two live workers while the map retained only the last — shutdown closed one, the other kept consuming, and dispatch resolved config from the first definition while the maps held the last. Validation now runs over the whole definition set **before any BullMQ object is constructed**, so a throw cannot leave orphaned Redis connections behind.

Also rejected at boot: empty names; non-integer or non-positive `maxConcurrent` / `concurrency` / `timeout` / rate limits / `repeat.every` / `repeat.limit`; negative `retries` / `cancelGraceMs` / `backoff.delay`; a blank `repeat.pattern`; and the same constraints on **`defaults`**, which are inherited by every job that omits the field — an invalid default is the per-job failure multiplied across the registry, and the per-job loop only sees explicitly-set values. `maxConcurrent <= 0` was the worst of these — it never releases a semaphore slot, so the job waits forever with no error and no timeout.

### `scopeRoleGate` delegates to `requireOrgRole`

It required an organization but then matched against `scope.userRoles`, so it disagreed with production for any actor whose global and org roles differ — `{ roles: ["employee"], orgRoles: ["manager"], organizationId: "org-1" }` was allowed by `requireOrgRole("manager")` and denied here. The tests could not catch it because `scopeFromTestActor` defaults `orgRoles` to `roles`, making both dimensions identical for every actor they built.

It is now a delegation rather than a second implementation, which also inherits the cases a hand-rolled org check kept missing: elevated scopes pass, and a service identity is refused with a message naming `requireServiceScope`. It returns an `AuthorizationDecision` (like every other check) instead of a bare boolean.

Arc carries no deprecation shims. Every alias below was a rename with no behaviour of its own; each has a one-for-one replacement.

| Removed | Use | Was |
|---|---|---|

### Static assets — `createApp({ assets })`

Users reporting "arc can't serve static data" were mostly hitting a HEADER, not a missing feature. Arc enables `@fastify/helmet` by default, whose defaults include `Cross-Origin-Resource-Policy: same-origin` — the browser then refuses to EMBED the response in any cross-origin document (`<img>`, `<audio>`, `<video>`, fonts). The request returns **200**, CORS negotiates correctly, and the body is silently discarded with `ERR_BLOCKED_BY_RESPONSE.NotSameOrigin`, which names neither CORS nor arc. A hand-rolled static route hit it too, because the header comes from the app rather than the route.

```ts
createApp({
  assets: [{ prefix: "/uploads", root: "./var/uploads", crossOrigin: "same-site" }],
})
```

`crossOrigin` sets CORP for **that prefix only** — the API surface keeps `same-origin` (pinned by a test). Arc supplies policy and delegates every mechanic to `@fastify/static`: byte ranges (audio/video seeking, verified 206 + `Content-Range`), `ETag`/`Last-Modified` conditional requests (verified 304), `immutable` directives, pre-compressed `.br`/`.gz` selection with `Vary: Accept-Encoding`.

Secure defaults, each chosen because the wrong value is silent: `cache: "revalidate"` (`immutable` on a mutable path serves stale bytes for a year — arc cannot know whether filenames are hashed); `disposition: "attachment"` (serving untrusted uploads `inline` is stored XSS via `.svg`/`.html`); dotfiles refused; directory listings off; `X-Content-Type-Options: nosniff` always. A duplicate prefix fails at boot naming both roots, rather than silently never serving the second.

Two documented traps: `allowedPath` is **synchronous** by `@fastify/static`'s contract, so an async `PermissionCheck` cannot run there — it is the seam for a signed-URL HMAC check, with a `preHandler` for async gates; and `preCompressed` selects the variant AFTER `allowedPath`, so denying `*.gz` does not stop `/main.js` serving `main.js.gz`.

New optional peer `@fastify/static >=8.0.0`.

### Per-route CORS — `RouteDefinition.cors`

One app-wide policy cannot serve an API and a public asset: the API wants `credentials: true` with a pinned origin list, the asset wants `origin: "*"`, and `*` + credentials is forbidden by the spec (arc already throws at boot on that pair). `cors` forwards to Fastify's `routeOptions.config.cors`, which `@fastify/cors` reads as a native per-route override; `false` disables CORS for the route. Arc forwards the value and lets the plugin own the semantics.

**⚠ Peer floor correction:** `@classytic/primitives` `>=0.15.0` → **`>=0.18.0`**. Arc's repository outbox adapter declares `OutboxStore.transactionalSave`, which is absent from the published 0.16.0 — arc's source required a version above its own declared floor. It was masked by a cp-dist'd local copy and surfaced when a clean install resolved the registry version. **Primitives 0.18.0 must publish before arc.**

### Zod schemas convert by DIRECTION — request as input, response as output

**A request body that used a `.default()` was rejecting legal requests.** `z.toJSONSchema()` emits either the input or the output shape and defaults to `output`; arc never passed the option, so every slot converted as output:

```ts
z.object({ title: z.string(), status: z.string().default("draft") })
// before → required: ["title","status"]   POST { title } ⇒ 400 "must have required property 'status'"
// after  → required: ["title"]            correct — the default supplies it
```

A `.transform()` was worse than wrong: unrepresentable in output mode, it degraded to `{}`, switching validation OFF for that property. Input mode emits the real input type.

`body` / `querystring` / `params` / `headers` (and `createBody` / `updateBody` / `listQuery` in OpenAPI) now convert as `input`; `response` and `entity` stay `output`. `toJsonSchema()` takes an optional 4th `io` argument (new `SchemaIo` type); the default is unchanged, so direct callers are unaffected.

**⚠ Behaviour change:** a plain `z.object()` no longer emits `additionalProperties: false` on REQUEST slots, so unknown keys are accepted where they were previously rejected. This is Zod's own semantics — `z.object()` STRIPS unknown keys rather than erroring, so they are legal input. Switch to `z.strictObject()` where the wire contract must reject them; it keeps the constraint in both directions.

### `openapi-3.1` no longer falls through unrecognized

Zod types `target` as `… | ({} & string)`, so an unknown value is not rejected — it matches no internal branch and silently gets draft-2020-12. `draft-7` is safe (Zod normalizes the alias to `draft-07`), `openapi-3.1` was not. Arc now maps it explicitly to `draft-2020-12`, which is the correct dialect since OAS 3.1 aligned with JSON Schema 2020-12.

Also: the unconvertible-schema error now names the actual fix for `z.date()` / `z.bigint()` on a request schema (use `z.iso.datetime()` / `z.string()` — JSON has neither type) instead of only mentioning `.refine`/`.transform`.

**⚠ Peer floor:** `zod` (optional) `>=4.0.0` → **`>=4.4.0`**. Arc's own code runs on 4.0, but 4.4 carries three fixes arc's output depends on: a stack overflow converting recursive `.lazy()` schemas that use `.describe()` (#5797), min/max intersections on the `openapi-3.0` target arc emits (#5700), and object/tuple optionality alignment (#5661) that the input/output split builds on.

### `describePermission` reports composed scope gates

`allOf` now merges its children's `_scopeContext`, and `describePermission` gained a `scoped` requirement kind carrying the scope dimensions (and any roles alongside). `allOf(requireRoles('admin'), requireScopeContext('branchRole','head_office'))` previously introspected as plain `roles` — so a FE permission matrix rendered an HQ-only action as available to every admin. `explainAccess` accepts the caller's `scope` to decide those gates, returning `conditional` when it isn't supplied rather than guessing.

Introspection only — `_scopeContext` never reaches enforcement, and evaluation is untouched. **Additive to a union**: a consumer with an exhaustive `switch` over `PermissionRequirement["kind"]` plus a `never` guard will need a `scoped` arm.

## 2.30.0 (2026-07-28)

> **⚠ Breaking:** `PermissionResult` (type) and `normalizePermissionResult` (runtime + type) are REMOVED from `.` and `@classytic/arc/permissions`. Migration at the end of this entry.

### Authorization: one decision contract, one enforcement point

A `PermissionCheck` now returns `boolean | AuthorizationDecision` — a decision is **pure data**, calculated the same way regardless of transport.

```ts
import { allow, deny } from "@classytic/arc/permissions";

const canRead: PermissionCheck = (ctx) =>
  isMember(scopeOf(ctx)) ? allow({ policy: { orgId: getOrgId(scopeOf(ctx)) } }) : deny("not a member");
```

Every surface funnels through ONE execution core (`evaluatePermissionDecision`, the transport-neutral PDP) and ONE enforcement point (`applyAuthorizationDecision`, the HTTP PEP). Previously each call site re-implemented the run/normalize/apply sequence inline and **drifted — action and aggregation routes dropped policy filters and scope entirely**. New: `allow`, `deny`, `applyAuthorizationDecision`, `evaluatePermissionDecision`, `normalizeToDecision`, `scopeOf`, types `AuthorizationDecision` / `DataPolicy` / `PermissionCheckReturn`.

`scopeOf(ctx)` is the single seam a check uses to read the request scope — so combinators can hand a child a NEW context instead of mutating `request.scope`, and non-HTTP transports (MCP, jobs, websockets) that have no request still resolve identity. `allOf`/`anyOf` evaluate purely: no request mutation, no rollback.

### Policy filters compose with AND (`conjoinPolicyFilters`)

Row-level filters arrive from independent sources in one request — a tenant preset, an `ownedByUser` grant, an `allOf` branch, a host check. Each is a RESTRICTION, so composition is logical AND. The historical `{ ...base, ...incoming }` spread did not implement AND: two sources constraining the same key meant the later one **silently replaced** the earlier, widening or erasing a restriction another layer deliberately imposed — a defense-in-depth defect. Non-overlapping filters (the ~99% case) produce a byte-identical object, so there is zero behavior change for them.

### Policy filters are portable across kits

Arc's helpers emit a Mongo-style operator dialect (`{ $or: [...] }`, `{ $in: [...] }`, and now `{ $and: [...] }`). Arc used to `Object.assign` those straight into the filter handed to `repository.getOne` / `getAll`. MongoKit compiles that natively; **SQLiteKit / PGKit did not** — repo-core's `recordToFilter` treats `$and`/`$or`/`$in` as literal column names, so a composed policy either threw or silently matched nothing. Filters are now normalized at the repository boundary.

### Aggregation reaches the kit in the same dialect as list

`toRepositoryFilter` now runs on the aggregation path too — inside `executeAggregation`, so the MCP tool surface gets it as well. Previously list normalized to the portable IR and aggregation handed the kit a raw `$`-record: identical on MongoKit (its compiler accepts both), but on SQLiteKit / PGKit a `$or` read as a literal column name. Deliberately applied at the repository call and NOT before the `materialized` hook — that hook is a host callback whose `filter` is arc's documented Mongo-record dialect.

`runAuthorizationConformance` gained an operator-policy case. The original one used a flat-equality policy, which passes through the normalizer untouched, so the two surfaces matched and the drift stayed invisible — the suite could not catch the very thing it exists for.

### `in` / `nin` on aggregations take a list

`?priority[in]=high,urgent` reached the kit as `{ $in: "high,urgent" }` — a string. MongoDB rejects `$in` on a non-array, so URL list-filters on aggregations were already broken; the test asserted only that the key existed, which hid it. The operand is now split on commas exactly as `ArcQueryParser` does for the CRUD list route — the contract this expansion always claimed to match.

### Fail-closed ownership

`ownedByUser` denies instead of sliding through: a request with no user (or no usable id) is rejected, and a record whose `ownerField` holds no value is **not** modifiable — `missingOwner: "allow"` is an explicit, bounded legacy opt-in. Previously an unowned record silently passed, which is the opposite of an ownership guarantee. **Check your `ownerField`**: it defaults to `userId`, and a mismatched name makes every record look unowned. Arc's own `examples/full-app` had exactly this bug — `presets: ["ownedByUser"]` over a `createdBy` column — so its gate allowed everyone; the example now uses `requireOwnership("createdBy", { bypassRoles: ["admin"] })`, the composable form that can express "the owner, or an admin" (the middleware preset bypasses only for elevated platform scope).

### Static analysis + conformance

`describePermission` / `describePermissionMap` / `explainAccess` / `collectPublicSurface` answer "who can do X, and why" WITHOUT running a request — the framework-owned version of the `/permissions/matrix` endpoint hosts hand-roll, so a UI's "can I?" and real enforcement can't drift. `allow`/`deny` are definitive from metadata; `conditional` means the gate reads request-time state and is never guessed.

`runAuthorizationConformance` (`@classytic/arc/testing`) runs the SAME permission through more than one surface and returns each one's status plus the exact filter arc handed the repository — proving CRUD and aggregation enforce identically. Runner-agnostic: it returns data, it does not assert.

### `strictPermissions`

An ungated write is a warning by default and **fatal** under `defineResource({ strictPermissions: true })` or `ARC_STRICT_PERMISSIONS=true`.

### Migration

| Removed | Use |
|---|---|
| `PermissionResult` | `AuthorizationDecision` (or `PermissionCheckReturn` for a check's return type) |
| `normalizePermissionResult` | `normalizeToDecision` |

### Module `eventHandlers`: opt-in error `boundary`

**`eventHandlers` gains an opt-in error `boundary`** — the last reason a module author would abandon the 2.24 arm and hand-roll `fastify.events.subscribe` in `afterResources`.

```ts
defineModule({ name: "search", eventHandlers: [
  { name: "search.reindex", event: "product:*", handler: reindex, boundary: true },
  { name: "search.audit",   event: "product:*", handler: audit,
    boundary: { onError: (err, e) => statsd.increment("handler.error", { type: e.type }) } },

```

Arc wraps the handler with `wrapWithBoundary`, logging through `fastify.log` with `{ err, event, eventId, handler }`. Unnamed handlers get a `<module>.<pattern>` label instead of `anonymous`, so a boundary log is always attributable.

**Off by default, deliberately.** A throw reaching the transport is what makes the durable path work — `RedisStreamTransport` leaves the message unacked, so it redelivers and eventually DLQs. Defaulting to swallow would silently downgrade every module handler to best-effort. Turn it on for fire-and-forget work (projections, cache invalidation, notification fan-out) where a failure must not block the ack and a retry would only delay the next event's resync.

Additive; existing `eventHandlers` declarations are unchanged.

### `HookContext.scope` — identity in a GLOBAL hook

 `ResourceHookContext` has carried a `scope` projection for inline `config.hooks`; the HookSystem context that cross-cutting hooks receive (`hooks.before('*', 'update', …)` — the canonical `updatedBy` stamp) did not, so hosts dug into the internal `context._scope` and fell back to `ctx.user?.id`, which is the auth adapter's unvalidated view.

```ts
fastify.arc.hooks.before("*", "update", async (ctx) => {
  if (ctx.scope?.userId && ctx.data) ctx.data.updatedBy = ctx.scope.userId;
});
```

Same `buildRequestScopeProjection` helper as `IRequestContext.scope` and `ResourceHookContext.scope`, so all three surfaces agree by construction — the resource-hook wrapper now reads the value through instead of re-deriving it. `undefined` on public/unscoped routes. Additive.

- `createIfPermitted` admission control (refuses a second non-terminal run on the same `concurrencyKey`, names the blocker, never writes the refused run; frees the key on terminal; never serializes key-free runs)
- `claim` exclusive lease (grants + counts the attempt, refuses a live lease, **recovers** a `running`/`finalizing` run whose lease expired, refuses terminal/unknown)
- `compareAndTransition` guarded CAS (applies status + patch, refuses a wrong `expected`, and refuses a **stale ex-owner's** token so a late `completed` cannot clobber the new owner)
- `requestCancel` durable flag (sets without changing status; idempotent — first request's audit metadata wins)
- `saveProgress` heartbeat (extends the lease for the owner; ignores a stale token)
- `reArmIfPermitted` retry (re-queues + clears cancel/lease/finalization; refuses non-terminal; refuses when another run holds the key — a retry must not slip a second destructive run past the guard)

Time is exercised via past/future lease `expiresAt` rather than a clock hook, so the suite runs unmodified against a real database.

### Performance — external-review wave 12 (scalability audit)

Nine-finding performance/scalability audit; all verified against source and fixed (benchmark lane + `arc doctor` query checks staged in v3.md).

- **Load shedding is ON by default** — `@fastify/under-pressure` defaults every threshold to 0 = disabled, so arc's presetless default was monitoring-only while appearing protective. The default now ships real event-loop thresholds (`maxEventLoopDelay: 3000`, `maxEventLoopUtilization: 0.98`); `productionPreset` gains the ELU threshold too (its 1 GB heap/RSS values remain placeholders to size from container limits). A production host config with NO threshold keys warns once at boot. `UnderPressureOptions` gains `maxEventLoopUtilization`.
- **Cache-stampede protection (single-flight)** — N concurrent misses on the same cache key used to issue N repository queries. `BaseCrudController` now coalesces same-key fills onto one in-flight query (per-instance map; keys already encode query + user/org scope + resource version, so coalescing cannot cross tenants), and a same-tick burst of stale readers schedules exactly ONE background SWR revalidation. New opt-in `QueryCacheConfig.jitter` (0–1) de-synchronizes expiry ACROSS keys.
- **Multipart memory is bounded per request** — per-file and per-count limits never bounded the SUM (`maxFiles: 5` × 10 MiB = ~50 MiB per request, multiplied by concurrency). New `maxTotalBytes` cap (default 25 MiB) returns 413 `arc.payload_too_large`; docs now state plainly the middleware is BUFFERED, for small uploads — large files belong on presigned direct-to-storage paths.
- **Outbox batch claim is ~2 round-trips, not N** — `repositoryAsOutboxStore.claimPending()` replaced its sequential one-CAS-per-row loop (batch 50 = 50 serial round-trips per relay tick) with a two-phase claim: ONE candidate fetch (claimable filter, FIFO, limit) then CONCURRENT per-id CAS writes that re-check the claimable filter (race losers drop out silently). An atomic limited batch-claim is not portable (Mongo `updateMany` has no limit) — SQL kits wanting `FOR UPDATE SKIP LOCKED` supply their own `OutboxStore`; `claimPending` IS the batch seam. `RelayResult` gains `claimMs`/`publishMs` phase timings.
- **Redis Streams: bounded batch concurrency (opt-in)** — new `processingConcurrency` option (default 1 = strict order preserved). Raising it worker-pools a batch's entries (used in both the read loop and the crash-recovery `xclaim` path); entries may then complete out of order, so raise only for order-independent handlers.
- **WS send-queue drain is O(1) per frame** — `flush()` used `Array.shift()` + full coalesce-map reindex per frame (O(n²) per drain under fan-out). ### Distributed-systems hardening — external-review wave 5

Production-architecture audit: nine findings verified against source; the contract and distributed-correctness gaps below fixed, one false positive rejected (events `failOpen: true` is a documented availability-first default with the outbox as the guaranteed path — the delivery matrix the review itself endorsed), and the structural remainder scheduled in v3.md.

- **Versioning plugin enforces a supported-version set** — `versioningPlugin({ versions: ['1','2'] })` rejects anything else with `400 arc.unsupported_api_version` (details list the supported set); `defaultVersion` outside the set fails boot. Docs now state plainly what the plugin is NOT: it detects/annotates/deprecates but does not route — version routing is `app.register(v2Routes, { prefix: '/v2' })` scopes or Fastify `constraints: { version }`. Without `versions`, detection-only mode is unchanged.
- **`MigrationRunner` is multi-runner safe** — new `lock` option (ecosystem `LockAdapter` shape, same `tryAcquire/release` contract as `arcPlugins.schedules.lock`): `up()/down()/downTo()` take the `arc:migrations` lease, FAIL FAST on contention, and re-read the applied set INSIDE the lease (two replicas booting together can no longer both compute the same pending set — the pre-fix TOCTOU). Applied records now carry a **sha256 source checksum** (`store.record()` gains an optional third `meta` arg — existing two-arg stores stay valid); editing an already-applied migration is detected on the next run (`checksumMismatch: 'warn'` default | `'error'`). **⚠ `downTo(migrations, target)` now throws when the applied set spans multiple resources** — versions are resource-scoped, and the old global numeric threshold silently rolled back UNRELATED resources; pass `downTo(m, target, { resource })`. Crash-window semantics (re-execution after crash-between-up-and-record) are documented as host concerns: idempotent migrations + deploy-job ownership, not hidden.
- **Query-cache invalidation is monotonic** — version bumps were `Date.now()` with a 24h TTL: same-millisecond bumps collided (entries cached between them stayed live), clock regressions moved versions BACKWARDS, and an idle resource's version expired back to 0 (reviving pre-reset entries). New optional **`CacheStore.increment(key, by?, ttlSeconds?)`** (the canonical repo-core `CacheAdapter` signature; Redis `INCRBY` — atomic and strictly monotonic across replicas) implemented by `MemoryCacheStore` (synchronous, no interleave) and `RedisCacheStore` (via optional `incrBy`/`expire` on `RedisCacheClient`; ioredis/upstash adapters map them automatically); fallback for plain stores is `max(now, current+1)` read-modify-write. TTL follows the repo-core contract — applied ON CREATE only, existing counters keep their original expiry — with a 1-year TTL on version keys (a year-scale reset can't collide with minutes-scale entry TTLs).
- **Idempotency fingerprint: over-deep bodies no longer false-replay** — everything past the depth cap (32) collapsed to one `"<truncated>"` sentinel, so two DIFFERENT deep bodies under the same key fingerprinted identically and the second request replayed the FIRST request's cached response. The over-deep subtree is now content-hashed (`<deep:sha256/16>`; unserializable subtrees keep the legacy sentinel); worst case is a false MISMATCH — the fail-safe direction. Plugin docs now state the guarantee honestly: **best-effort effectively-once**, not exactly-once — the domain write and the idempotency record are different systems; for unacceptable re-execution windows, record idempotency in the business transaction or make handlers naturally idempotent.
- **Circuit breaker: half-open probe fencing + abort propagation** — after `resetTimeout`, EVERY queued caller used to observe "eligible" and rush the barely-recovered dependency simultaneously; now `halfOpenMaxProbes` (default 1) callers probe and the rest fail fast (or hit the fallback) as if still open. Opt-in `propagateAbort: true` hands the wrapped fn a trailing `AbortSignal` fired on timeout, so timed-out work stops holding sockets/pool slots instead of running to completion behind the rejected caller.
- **Webhook delivery retry (opt-in)** — `webhookPlugin({ retry: { attempts, backoffMs } })`: exponential backoff on transient failures only (network errors, timeouts, 429, 5xx — other 4xx/3xx are final), fresh signature+timestamp per attempt, CONSTANT `x-arc-webhook-delivery` id so receiver dedup treats retries as one delivery; `deliveryLog()` records gain `attempts`. Default stays single-attempt. Documented as best-effort in-process — guaranteed delivery is a durable-job concern (outbox + worker), scheduled in v3.md.
- **Distributed-runtime guard: schedules coverage + honest scope** — `runtime: 'distributed'` now warns when `arcPlugins.schedules` is configured without a `lock` adapter (every replica fires every tick). The guard's scope is documented at the check site: it validates what `createApp` can see (`stores` + `arcPlugins`); subsystems wired inside `plugins()`/`bootstrap[]` are the host's checklist in `wiki/delivery-guarantees.md`.
- **Query joins: dev-time allowlist nudge** — `populate=`/`lookup=` without `allowedPopulate`/`allowedLookups` is allow-ALL (client-driven N+1 / expensive-join surface). One-shot non-production warning teaches the allowlist during development; flipping the default to deny is scheduled for v3.

### repo-core standardization + reliability — external-review wave 6

Audit of arc against repo-core's canonical contracts (all findings verified against BOTH sources). One critical incompatibility, four reliability fixes, three consolidations; the QueryCache→CacheEngine façade migration is scheduled, not half-built (v3.md).

- **⚠ CRITICAL: `CacheStore.increment` realigned to the canonical `CacheAdapter` signature `(key, by?, ttlSeconds?)`** — the wave-5 addition had drifted to `(key, ttlSeconds?)`, so a conforming repo-core adapter plugged into `QueryCache` read the one-year TTL as the INCREMENT AMOUNT (+31.5M per version bump, and no TTL applied). `CacheStore` now `extends CacheAdapter` (`@classytic/repo-core/cache`) so any future drift is a compile error, and a conformance test runs repo-core's real memory adapter through `QueryCache`. `RedisCacheClient.incr` → `incrBy(key, by)` (Redis `INCRBY`); ioredis/upstash adapters map it automatically. Both signatures are 2.24-unreleased — no published consumer existed.
- **⚠ `withRetry` no longer acknowledges events it failed to dead-letter** — when retries exhaust AND `transport.deadLetter()` itself throws, the wrapper used to log and return; on at-least-once transports that ACKED the message with the event neither processed nor persisted — silent loss. It now RETHROWS (transport keeps the original pending and redelivers); `dlqFailureMode: 'log-and-drop'` opts back into loss for disposable events. The Redis Streams transport's own DLQ path already ordered ack-after-DLQ-write correctly.
- **Job timeouts now signal cancellation** — `JobMeta.signal: AbortSignal`, aborted when the job's `timeout` elapses. `Promise.race` alone released the concurrency semaphore while the handler kept running, so a BullMQ retry could overlap the original execution against the same data. Handlers pass the signal to fetch/DB calls; handlers that ignore it must be idempotent under overlap (documented on the field).
- **Schedule leases renew while the handler runs** — same-holder `tryAcquire` extends the lease (the `LockAdapter` contract capability arc wasn't using), renewed at `leaseMs/2` intervals. Pre-fix a handler outrunning its lease (default cap 5 min) let another replica overlap it — the exact overlap the lock exists to prevent. Lost renewal logs a warning (fencing tokens are the stronger v3 answer).
- **Health checks receive an `AbortSignal`** — `check(signal?)`, aborted at the check's timeout, so a stalled dependency probe can actually STOP instead of leaking an abandoned operation per readiness poll. Zero-arg checks unchanged.
- **⚠ Compensation `fireAndForget` steps are no longer reported as completed** — they were pushed to `completedSteps` BEFORE executing and their rejection was swallowed silently, so a "successful" result could name a step that later failed. They're now outside the transactional result entirely (not in `completedSteps`/`results`, never compensated — which was already true) and rejections surface via `hooks.onStepFailed`. Durable side effects belong in the outbox/jobs, not fire-and-forget steps.
- **⚠ Lock contract consolidation — one standard, no aliases** — `ScheduleLockLike` and `MigrationLockLike` are REMOVED; `arcPlugins.schedules.lock` and `MigrationRunnerOptions.lock` are typed as the canonical `LockAdapter` (`@classytic/repo-core/lock`) directly. The structural mirrors predated the `/lock` subpath; the `>=0.14` peer floor ships it, and both names were 2.24-unreleased, so no published consumer breaks. Import the type from repo-core.
- **Usage contract consolidation** — `@classytic/arc/usage` re-exports `UsageStore`/`UsageBucket`/`usagePeriod` from `@classytic/repo-core/usage` instead of maintaining the structural mirror (same obsolete-reason as locks).
- **`scheduleBackground` re-exported from repo-core** — arc's local copy fell back to `queueMicrotask` on non-Node runtimes, which flushes BEFORE the response I/O phase completes (an SWR refresh could delay the user's response write); the canonical helper defers past the I/O phase on every runtime (`setImmediate` / `setTimeout(0)`).

### Failure-safety closure — external-review wave 7 (re-audit of wave 6)

All seven re-audit findings verified and fixed — no deferrals:

- **⚠ `eventPlugin` DLQ store failures now propagate** — the plugin wired `deadLetterQueue.store` through `onDead`, the observability slot whose failures are swallowed, so the STANDARD config (`eventPlugin({ retry, deadLetterQueue })`) could acknowledge an event after both its handler and durable DLQ storage failed — the exact loss path wave 6 fixed for direct `withRetry({ transport })` use. `withRetry` now has a durable **`deadLetter`** option (failure follows `dlqFailureMode`, rethrow default) distinct from **`onDead`** (metrics/alerts, failures logged and contained); the plugin wires its store/`$deadLetter` publisher through `deadLetter`. Regression-tested through `eventPlugin` end-to-end with a propagating transport.
- **`increment` TTL semantics now match repo-core exactly** — the wave-6 fix aligned the SIGNATURE but not the runtime contract: repo-core applies `ttlSeconds` ON CREATE only (existing counters keep their original expiry — `EXPIRE ... NX`); arc's adapters reset it every call. Memory store keeps the live entry's expiry; Redis store calls `EXPIRE` only when `INCRBY` returned exactly `by` (key just created — no Redis 7 requirement). Conformance-tested against repo-core's reference memory adapter. The year-scale version-key reset this implies cannot collide with minutes-scale entry TTLs (documented at the call site).
- **Schedule lease renewal is serialized** — `setInterval` around an async lock call could stack overlapping `tryAcquire`s against a slow backend, and teardown didn't await an in-flight renewal (a late one could extend the lease after the run settled). Now a recursive-timeout loop (next renewal only after the previous settles) with awaited teardown. Same loop added to **`MigrationRunner`** — migration leases renew at `lockLeaseMs/2`, so a migration slower than the lease no longer lets a second deployment start migrating concurrently (operators stop guessing the slowest migration).
- **⚠ Job bulkhead holds until the handler SETTLES** — `maxConcurrent` released its semaphore when the timeout race rejected while the handler kept running, so a BullMQ retry could stack live executions past the limit. The slot now frees on actual handler settle, bounded by new **`cancelGraceMs`** (default 30s) so a handler that ignores `meta.signal` forever can't wedge the queue (force-release is logged loudly); a timed-out handler's eventual settle is logged for observability. `maxConcurrent` docs now state the guarantee precisely.
- **Compensation hooks are contained everywhere** — a THROWING observability hook could (a) become an unhandled rejection from the detached fire-and-forget chain, and (b) on the main path, a throwing `onStepComplete` was caught by the step's try block and MISATTRIBUTED as step failure — observability triggering compensation of a step that succeeded. Every hook invocation now goes through a contain-and-continue guard (`safeHook`); the detached chain ends in a final `.catch` backstop.

(2) REDIRECTS: `fetch` follows 3xx by default, so an allowed public URL could 302 into a blocked private/metadata target; with a policy active, delivery now runs `redirect: "manual"` and a 3xx records as a failed delivery. `defaultWebhookUrlPolicy` also gains the missing address families: IPv6 loopback/unspecified (`::1`, `::`), unique-local `fc00::/7`, link-local `fe80::/10`, `0.0.0.0/8`, and IPv4-mapped IPv6 in BOTH spellings (WHATWG URL canonicalizes `::ffff:169.254.169.254` into hex groups `::ffff:a9fe:a9fe` — the dotted form alone never matches post-parse; arc decodes both back to dotted-quad and applies the v4 rules).
- **`resolveOrgFromHeader` rejects a REPEATED org header with 400** (`ValidationError`) instead of casting the runtime array into a string — duplicate tenant-selection headers are a smuggling signal; neither value can be trusted to steer the membership check. First consumer of the duplicate-header posture `getHeader()`'s docs prescribe.
- **`toFetchHandler` size-limit docs made precise** — declared `Content-Length` over the limit is rejected BEFORE buffering; chunked/undeclared bodies are necessarily buffered first and checked after (a consequence of the buffered-adapter design). Platform/gateway body limits remain the real pre-allocation protection.
- **`productionPreset.trustProxy: true` acknowledged as an informed tradeoff, not fixed** — the boot warning stands for v2 (flipping the default mid-major would break every proxied production host in the silently-wrong direction); the fail-closed flip to `false` is now formally scheduled in v3.md, and the warning tells hosts to set an explicit value to be upgrade-proof.

### Security & correctness — external-review wave 2 (all six claims verified real)

- **Webhook v1 signing contract** — the legacy HMAC signed the BODY ONLY, so a captured request replayed forever, and the event id rode an UNSIGNED header (replay + dedup-defeat). New contract signs `v1.<timestampMs>.<deliveryId>.<body>` → headers `x-arc-webhook-signature: v1=<hex>` + `x-arc-webhook-timestamp` + `x-arc-webhook-delivery` (= event `meta.id`, stable across retries so receivers dedup on an AUTHENTICATED id). New `signWebhook` / `verifyWebhook({ toleranceMs = 5min })` — verifies signature + timestamp window, returns the authenticated delivery id; errors are typed (`missing_headers` / `bad_timestamp` / `expired` / `bad_signature`). Legacy `x-webhook-signature`/`x-webhook-id` headers still emitted for existing receivers (deprecated, removal in v3).
- **Webhook SSRF seam** — `webhookPlugin({ validateUrl })` runs on the parsed URL at `register()` time (throw = reject); opt-in `defaultWebhookUrlPolicy` requires HTTPS and blocks loopback/link-local/private-network/cloud-metadata hosts. Deliberately NOT default (internal webhooks to private services are legitimate) and deliberately not DNS-resolving — rebinding protection belongs at the outbound network boundary. Unparseable URLs now always reject.
- **⚠ `webhooks.list()` no longer returns secrets** — enumeration is safe for admin UIs; `webhooks.getSecret(id)` is the separate privileged path. Hosts reading `list()[n].secret` must switch.
- **`webhookPlugin({ concurrency })` validates `>= 1` integer at boot** — `concurrency: 0` made the delivery loop splice empty batches forever (silent hang on first event).
- **⚠ `resolveOrgFromHeader` throws canonical ArcErrors** (`UnauthorizedError` 401 / `OrgAccessDeniedError` 403) instead of hand-rolling the legacy `{ success, error, message }` envelope — responses now flow through the global error handler's `ErrorContract` (code/status/details), consistent with every other arc surface. Wire shape changes for those error paths. Also fixes role loss: upgrading authenticated → member now PRESERVES adapter-resolved `scope.userRoles` (JWT `roles` claim etc.) instead of re-deriving from `user.role` alone.
- **Edge adapter is now honestly a buffered fetch bridge** — `toFetchHandler` reads bodies as raw bytes (`arrayBuffer()` — `text()` UTF-8-decoded and corrupted binary payloads), returns `rawPayload` (binary responses intact), replaces the cold-start `ready` boolean with ONE shared readiness promise (concurrent first requests can't race past boot), and gains `maxRequestBytes` (default 1 MiB, `0` disables) returning 413 `arc.payload_too_large` BEFORE buffering. Docs now state plainly what `.inject()` buffering cannot do: SSE/streaming responses, WebSocket upgrades, cross-adapter backpressure — for edge realtime, publish to a Worker/Durable-Object tier instead.
- **`preset: 'production'` warns when `trustProxy: true` is inherited** — the preset trusts EVERY proxy so single-LB apps work out of the box, but if the app is reachable without the proxy, clients spoof `X-Forwarded-*` (rate-limit bypass, wrong audit IPs, forged proto). One boot WARN fires only when the host didn't set `trustProxy` explicitly; any explicit value (hop count, CIDR, function, or a deliberate `true`) silences it. A framework can't know the host's proxy topology — no discovery magic, just the nudge.
- **`ApiResponse` deprecated** — the `{ success, data, error, message }` envelope hasn't been arc's wire contract for a long time (successes: direct data via `IControllerResponse`; errors: `ErrorContract`), but the exported type kept teaching new apps and AI agents the obsolete shape. Removal in v3.
- **`ArcHeaders` + `getHeader()`** (`@classytic/arc/utils`) — Node/Fastify header values are `string | string[] | undefined` at runtime, but `IRequestContext.headers` declares the narrower `Record<string, string | undefined>` (the HTTP adapter passes Fastify's object through). One honest type + one duplicate-deterministic accessor (first value; consumers caring about smuggling reject arrays) serving both HTTP and synthetic MCP contexts. The declared type widens to `ArcHeaders` in v3.

### New — `realtimePlugin` (permission-aware resource change feed)

- **`arcPlugins: { realtime: true }`** → `GET /realtime/:resource` streams that resource's `created/updated/deleted` CRUD events over SSE, gated by the resource's OWN `list` permission: the check runs once at connect (canonical 401/403 shapes), its row filters apply PER EVENT in process (adapter `matchesFilter` or `simpleEqualityMatcher` for flat equality), org-carrying events are tenant-guarded, and field-level read permissions mask every payload. Fail-closed: operator-shaped filters without an adapter matcher reject the subscription (501 `arc.realtime.unfilterable` + fix hint). Non-goals by design: no replay/resume (change NOTIFIER, not an event store — outbox covers guaranteed delivery), no presence/broadcast (`app.events` + sse already do). Architecture: event-driven off arc's existing CRUD event bridge — no WAL polling, no per-item ACL walks, authorization-correct by construction. **Multiplexing:** `GET /realtime?resources=a,b,c` — N feeds over ONE connection (cap 20; the Phoenix-channels/Pusher concern answered at the URL level, no custom protocol), each resource authorized independently with an isolated filter snapshot; any denial rejects the whole subscription (fail-closed, names the resource). Frames carry the WHATWG SSE `id:` field (client `lastEventId` dedup without server replay) + a `retry:` reconnection hint. SSE transport mechanics extracted to `utils/sseStream.ts` (hijack/CORS-merge/heartbeat/backpressure/id/retry), shared by sse + realtime; `RegistryEntry.fields` now surfaces the live field-permission map for request-time masking. Pure policy (`resolveRowMatcher`, `resolveDelivery`, `buildChangeFrame`) exported for unit tests — the handler is orchestration only.
- **Membership transitions + staleness bound.** The architecture was validated as sound (authorize at connect, fan out, match in-memory) — the validation pass surfaced two real gaps, now fixed: (1) **Leave-detection** — when an UPDATE moves a record OUT of a subscriber's row filter (owner reassigned, soft-deleted, moved org), the feed emits a synthetic `<resource>.left` frame (`{ id }`) so the client drops the now-invisible row, instead of silently dropping the update and leaving a permanently stale row. This is the "row left the result set" signal every mature realtime system sends; the ENTER transition needs no special frame (the matching `updated` frame carries the record). (2) **Permission-staleness bound** — filters are snapshotted at connect, so a revoked caller kept their old view until reconnect; the feed now force-closes at the auth token's `exp` (→ reconnect → fresh authorization), with a `maxConnectionMs` cap for session/cookie auth carrying no `exp`. Also: the connect-time filter probe now catches an adapter matcher that throws on an unsupported operator and rejects cleanly (501) instead of crashing the subscriber's stream per-event. The shared matcher (`@classytic/repo-core/filter`) gained a prototype-key denylist + `$regex` input cap + a mongokit⇄real-MongoDB differential drift-gate — see repo-core 0.14.0.

- **⚠ CORS `origin: '*'` + `credentials: true` now throws at boot** (was: silent rewrite to `origin: true`, i.e. reflect ANY request Origin with credentials — the exact vulnerability the browser wildcard ban prevents). The error lists the three valid fixes: explicit allow-list, pattern, or `credentials: false`.

**Second wave (same audit, deeper cuts):**

- **⚠ Auth moved from `preHandler` to route-level `onRequest`** — all three routers (CRUD, actions, aggregations) now compose hooks via `buildRouteHooks` → `{ onRequest: preAuth → arcDecorator → authMw, preHandler: permissionMw → pluginMw → routeGuards → customMws }`. Fastify parses the body and runs AJV BETWEEN the two stages, so unauthenticated requests 401 before paying parse/validate cost — and before a 400 could leak schema shape to anonymous callers. Auth reads only headers/cookies/params/query (available at onRequest); everything body-shaped stays at preHandler. Elevation is unaffected (it wraps the `authenticate` decorator, not a hook). Host-visible deltas: unauthenticated requests with invalid bodies now get **401 instead of 400** (including action posts, where the `attachValidation` formatter previously ran before auth); custom routes registered via `preHandler: [fastify.authenticate]` keep working unchanged. `buildPreHandlerChain` (internal) is replaced by `buildRouteHooks`/`routeHookOptions`. Pinned by `tests/core/auth-before-parse.test.ts`; zero regressions across the ordering-sensitive suites (idempotency, response-cache, multiTenant, RBAC, elevation).
- **List route serializer: merged shape instead of top-level `oneOf`** — `listResponse()` now emits ONE permissive object covering all four canonical variants (offset / keyset / aggregate / bare) instead of a `oneOf` union. fast-json-stringify implements top-level `oneOf` by running full AJV validation PER RESPONSE to pick the branch — on the hottest route of every arc app. Wire bytes are identical (all four variants were `additionalProperties: true` supersets with non-conflicting properties; pinned byte-for-byte by `tests/utils/list-response-serialization.test.ts`). ### New — `usage` plugin (`@classytic/arc/usage`)

### New — plan-aware rate limits (`rateLimit.plan`)

- **`rateLimit.plan: { resolve, limits, default }`** — resolve the caller's plan per request (`resolve(req)` → `'free' | 'pro' | ...`) and apply that plan's ceiling (`limits: { free: { max: 60 }, pro: { max: 1000 }, enterprise: false }`; `false` = effectively unlimited). ### Added

- **Modules — domain composition** (`@classytic/arc/factory`): `defineModule()` bundles a domain package's `plugins` + `bootstrap` + `resources` + `afterResources` + `onClose` as one `ArcModule<TExports>` value; `createApp({ modules })` expands each into the SAME fixed lifecycle phases a hand-wired app uses (modules before app-level entries; `onClose` in reverse composition order). Entries may be eager modules, promises, or **thunks of dynamic imports** — unselected thunks are never evaluated (region/tier packs stay out of the process entirely). A `bootstrap` return value becomes the module's public export at `fastify.arc.modules[name]`; read it back with the typed throwing accessor **`getModuleExports(fastify, name)`** — no DI container, no casts at either end. Replaces "encode order by list position," which broke silently on a re-order or a conditionally-inserted module. ## 2.17.0

Stabilization + security release. Closes five silent-drop classes (each previously cost a host hours to debug), shuts the prototype-pollution door on every untrusted JSON boundary arc decodes, bounds the idempotency fingerprint hot path against deep-nesting DoS, ships an exported `buildScope` + scope-threading fix that MCP-driven hosts have been hot-patching locally, and adds `GET /jobs/:id/status` + per-job `maxConcurrent` semaphore on the jobs integration. No breaking changes — every behavior change is either a new guard, a new diagnostic, or a fix to a silently-broken contract.

### Security — prototype pollution on untrusted JSON

Arc already declared `secure-json-parse@^4.1.0` as a direct dep but only used it in `createApp.ts`'s content-type parser override. Five other trust-boundary sites decoded JSON with raw `JSON.parse`, leaving Object.prototype poisoning open to anyone who could put bytes on those boundaries:

- `src/auth/redis-session.ts` — session payloads read back from Redis (anyone with Redis write access could pollute every consumer's prototype on the next session load).
- `src/events/transports/redis.ts` — cross-service Redis pub/sub event payloads.
- `src/events/transports/redis-stream.ts` — cross-service Redis Streams entries.
- `src/integrations/websocket/connection.ts` — untrusted WebSocket client frames.
- `src/middleware/multipartBody.ts` — attacker-controlled multipart text fields parsed opportunistically as JSON.

All five now route through `sjson.parse` (with reviver preserved on the two transports that use one for `Date` revival). Lock-in: `tests/security/prototype-pollution-untrusted-json.test.ts` — exercises every boundary with a `{"__proto__":{"polluted":"yes"}}` payload and asserts `Object.prototype.polluted` remains undefined after.

### Security — idempotency fingerprint depth-bomb

`normalizeBody()` in `src/idempotency/idempotencyPlugin.ts` recursed unbounded over the request body to produce a key-stable fingerprint. Fastify's 1 MiB `bodyLimit` bounds total payload size, but a 1 MiB JSON body shaped as `{"a":{"a":{...250K levels...}}}` still nested deep enough to blow the V8 stack mid-hot-path. Pre-fix that landed as an unhandled `RangeError: Maximum call stack size exceeded` inside the idempotency preHandler — the worker died mid-request.

Post-fix: a `MAX_FINGERPRINT_DEPTH = 32` cap substitutes a `"<truncated>"` sentinel past the cap so the hash still differs from siblings, recursion is bounded, and real APIs (which essentially never exceed depth 10) are untouched. Lock-in: `tests/idempotency/fingerprint-depth-bomb.test.ts` (1000-deep payload through the full plugin path).

### MCP — exported `buildScope` + `evaluatePermission` scope threading

Two related bugs that hosts (notably fajr-be-arc) had been hot-patching against the published dist:

1. **`buildScope` was not exported** from `src/integrations/mcp/buildRequestContext.ts`. Now exported as a public-stable helper for MCP tool authors that need to resolve an `McpAuthResult` into a canonical `RequestScope` (e.g. when constructing the permission-check context themselves).

2. **`evaluatePermission` in `src/integrations/mcp/tool-helpers.ts` did not populate `request.scope` on the fake request it built for the permission check.** HTTP paths populate BOTH `request.scope` (auth adapter) AND `request.metadata._scope` (`applyPermissionResult`) — and helpers like `requireOrgMembership()` read from `request.scope` via `getRequestScope(req) = req.scope ?? PUBLIC_SCOPE`. With neither populated on the MCP fake-request, every authenticated MCP call rejected as "Organization membership required" even when `session.organizationId` was present. Post-fix calls `buildScope(session)` and threads the result through both slots.

Lock-in: `tests/integrations/mcp/mcp-fake-request-scope.test.ts` — 7 cases pinning `requireOrgMembership` + `requireOrgRole` on authenticated and anonymous MCP sessions, plus the `buildScope` export contract.

### DX — auto-apply field-write permissions on custom routes

Auto-CRUD's create/update routes have always run user-declared `fields: { x: fields.writableBy(['admin']) }` rules through `BodySanitizer` inside `BaseController`. Custom routes — `config.routes`, presets — never went through that path. ### `defineResource({ mcp: false })` — per-resource MCP opt-out

### Streamline `/start` body-envelope validation

`POST /:workflowId/start` now validates the body envelope at the route boundary and throws a 422 with an actionable message instead of letting the request reach the engine and surface as a cryptic `"Invalid Date"` 400 from a downstream validator ([`src/integrations/streamline.ts`](src/integrations/streamline.ts)).

Three new error codes:

| Code | Trigger | Status |
|------|---------|--------|
| `arc.streamline.invalid_body` | Non-object body (string, array, number) | 422 |
| `arc.streamline.missing_input_envelope` | Top-level workflow fields without an `input` wrapper (`{ orderId: '123' }` instead of `{ input: { orderId: '123' } }`) | 422 |
| `arc.streamline.unknown_envelope_keys` | Extra keys alongside `input` outside the canonical envelope (`input` / `meta` / `idempotencyKey` / `priority`) | 422 |


Empty-body submissions (parameterless workflows) pass through unchanged.

### QueryParser — bracket-envelope filter form

`ArcQueryParser` now accepts BOTH filter notations ([`src/utils/queryParser.ts`](src/utils/queryParser.ts), [`src/constants.ts`](src/constants.ts)):

| Form | Example | Use when |
|------|---------|----------|
| Bare (legacy, default) | `?status=active&price[gte]=40` | Short queries; matches arc's pre-2.16 behaviour |
| Bracket envelope | `?filter[status]=active&filter[price][gte]=40` | REST-conventional (JSON:API / Stripe / Plaid style); safe on busy URLs that might collide with reserved meta keys (`page`, `sort`, `select`, ...) |

Both forms produce identical `filters: { status: 'active', price: { $gte: 40 } }`. Operator notation (`[gte]`, `[lte]`, `[ne]`, `[in]`, `[contains]`, ...) works inside either form. Operator whitelist + field whitelist + ReDoS protection apply equally.

Precedence on key clash (mixing both forms): **bare wins** (`?status=closed&filter[status]=active` → `{ status: 'closed' }`). Deterministic, documented; mixing should be rare.

**Parser portability note.** Other parser implementations (`@classytic/mongokit`'s `QueryParser`, custom hosts-side parsers) may accept only the bare form. When swapping `queryParser` to a different implementation, double-check which forms it understands before publishing URLs that mix the two — this is also documented in the `ArcQueryParser` JSDoc.

### Fix — `multiTenantPreset` now wires `/aggregations/:name` routes

Pre-2.15.3 a resource declared with `presets: [multiTenantPreset({ tenantField: 'organizationId' })]` had its CRUD list correctly tenant-scoped but its auto-generated `/aggregations/:name` routes **leaked aggregated rows across orgs** for any caller whose `scope.kind !== 'member'`.

1. **[`src/presets/multiTenant.ts`](src/presets/multiTenant.ts)** — preset now emits `aggregations: [strictTenantFilter]` alongside the five CRUD slots. Always strict (no flexible variant — aggregations have no public-list semantic).

3. **[`src/core/defineResource/plugin.ts`](src/core/defineResource/plugin.ts)** — passes `resource.middlewares?.aggregations` through to `createAggregationRouter`.
4. **[`src/core/BaseCrudController.ts`](src/core/BaseCrudController.ts)** — `tenantRepoOptions` now emits `bypassTenant: true` when the scope is `kind: 'elevated'` AND no specific tenant target was resolved. ### Why CRUD list worked but aggregation didn't (pre-fix)

`multiTenantPreset`'s strict / flexible filters write BOTH `request._policyFilters` AND `request._tenantFields`. `BaseCrudController.list` merges `_policyFilters` into the query before delegating to `repo.getAll`. The aggregation router has no equivalent — it consults `tenantRepoOptions` which only reads `metadata._scope` (path 1) + `_tenantFields` (path 2). Without the preset's preHandler running on aggregation routes, `_tenantFields` was never set; for callers without `scope.kind === 'member'`, neither path resolved an `organizationId` and the AggRequest reached the kit unscoped.

The pre-2.15.2 advice to use `scope: false` "to avoid double-scoping with arc" is no longer correct — arc 2.15.2+ deliberately leaves `aggReq.filter` clean and relies on the kit. Fitverse had this right (`scope: { fieldType: 'objectId' }`); shajghor's `scope: false` was the second half of the leak.

## 2.15.0

Five DX wins on the `defineResource()` + `BaseController` seam, all bundled with the **2.14.3 aggregation tenant-scope fix** that originally shipped on its own. Net change for hosts: less bookkeeping, fewer false-positive warnings, and a typed seam between resource-level and controller-level options.

### Migration — one behavior change to watch

`setQueryParser` was a soft warn pre-2.15 and is a registration-time **throw** in 2.15.0. If you have a custom controller (one that doesn't extend `BaseController` / `BaseCrudController`) AND set `queryParser` at the resource level, arc refuses to register the resource at boot. **Two fixes:**

1. Extend `BaseController` / `BaseCrudController` — both implement `setQueryParser` natively.
2. Add a `setQueryParser(qp): void` method on your controller that **wires the parser into your query resolution path**. A no-op is not a fix — it lies to arc about a real misconfig and re-creates the silent-drift bug the throw exists to prevent.

There is no escape hatch by design. If `queryParser` is set at the resource level, arc guarantees it reaches the controller; if it can't, the resource doesn't register. This is the same fail-closed posture arc takes for `isRevoked`, security headers, and field-write denial. **No other behavior change is breaking** — `_declaredKeys`, `configure()`, and the layer-split types are purely additive; the dropped-options warn now fires LESS often (only on user-declared keys), never more.

## 2.13.0

### BREAKING — wire envelope removed (no `{success, data}` wrapper)

Arc no longer wraps responses in `{success: true, data: ...}` / `{success: false, error: ...}`. The wire shape is now what the controller returns directly; HTTP status discriminates success vs error. This unifies arc with Stripe / GitHub / Shopify-style REST conventions and removes the JSON-RPC-era envelope that was the only impurity in arc + arc-next + repo-core's contract chain.

#### What changed on the wire

| Endpoint | Before (≤2.12) | After (2.13) |
|---|---|---|
| `GET /users/:id` | `{success: true, data: {_id, name, ...}}` | `{_id, name, ...}` |
| `POST /users` | `{success: true, data: {...}, status: 201}` | `{_id, name, ...}` (status 201) |
| `GET /users` (paginated) | `{success: true, docs: [...], page, ...}` | `{method: 'offset', data: [...], page, limit, total, pages, hasNext, hasPrev}` |
| `GET /users` (bare) | `{success: true, docs: [...]}` | `{data: [...]}` |
| `DELETE /users/:id` | `{success: true, data: {message, id, soft?}}` | `{message, id, soft?}` |
| Any 4xx / 5xx | `{success: false, error: '...', code: 'NOT_FOUND', timestamp, requestId, details}` | `ErrorContract` from `@classytic/repo-core/errors`: `{code, message, status, details?, meta?, correlationId?}` |

#### What changed on the field name

- Pagination shape field renamed `docs` → `data`. All four pagination shapes (`OffsetPaginationResult`, `KeysetPaginationResult`, `AggregatePaginationResult`, `BareListResult`) carry `data: TDoc[]` in repo-core 0.5+.
- `BareListResponse` → `BareListResult`. `*PaginationResponse` types removed (use `*PaginationResult` directly — they were structurally identical aliases). `PaginatedResponse` → `PaginatedResult` (now includes the bare-list arm).
- `DeleteResult` drops the `success: boolean` field — kits return `Promise<DeleteResult | null>` (`null` on miss, matching `update()`'s convention). Same shape arc emits on the wire.

#### What changed for handler authors

- **Errors throw, never return.** Replace `return { success: false, error: '...', status: 404 }` with `throw new NotFoundError(...)` (or any `ArcError` subclass). The global error handler catches and emits the canonical `ErrorContract`.
- **Success returns drop `success: true`.** `return { success: true, data: doc, status: 201 }` → `return { data: doc, status: 201 }`.
- `IControllerResponse<T>` now just `{ data: T; status?; headers?; meta? }`.
- `BaseCrudController.notFoundResponse(...)` removed — throw `new NotFoundError(...)` instead.
- Hierarchical error codes: `'NOT_FOUND'` → `'arc.not_found'`, `'VALIDATION_ERROR'` → `'arc.validation_error'`, `'FORBIDDEN'` → `'arc.forbidden'`, `'CONFLICT'` → `'arc.conflict'`, etc. (Cross-cutting canonical codes live in `@classytic/repo-core/errors`'s `ERROR_CODES`.)
- `envelope()` helper, `reply.ok()` / `reply.fail()` / `reply.paginated()` removed. `reply.sendList(input)` (canonical pagination) and `reply.stream(...)` (downloads) stay. Single-doc handlers just `return data` or `reply.send(data)`.
- `ArcError.toJSON()` removed — handler owns serialization.

#### Single source of truth across the ecosystem

| Package | Owns |
|---|---|
| `@classytic/repo-core/pagination` | `OffsetPaginationResult`, `KeysetPaginationResult`, `AggregatePaginationResult`, `BareListResult`, `PaginatedResult`, `toCanonicalList` |
| `@classytic/repo-core/repository` | `DeleteResult`, `DeleteManyResult`, `UpdateManyResult`, `BulkCreateResult`, `BulkWriteResult` |
| `@classytic/repo-core/errors` | `HttpError`, `ErrorContract`, `ErrorDetail`, `toErrorContract`, `isHttpError`, `ERROR_CODES` |
| `@classytic/arc/utils/errors` | `ArcError` + 8 subclasses (all implement `HttpError`) |

Mongokit / sqlitekit / prismakit return these canonical shapes from `getAll` / `delete` / `bulkCreate` / etc. Arc emits them on the wire unchanged. Arc-next types its return values against the same shapes. **One declaration, three layers, zero drift.**

#### Consumer migration

- **HTTP/UI consumers** (apps reading `res.json()`): rename `body.docs` → `body.data` for paginated lists; drop the `body.data` unwrap for single-doc reads (the doc is now top-level); switch error checks from `body.success === false` to `!res.ok` (status discriminates); error code matchers from `body.code === 'NOT_FOUND'` to `body.code === 'arc.not_found'`.
- **`arc-next` typed client** consumers: `await api.users.getById(id)` returns `User` directly (was `ApiResponse<User>`); `await api.users.delete(id)` returns `DeleteResult` directly. Errors throw `ArcApiError` (was returned as `{success: false, error}`).
- **Direct kit consumers** (server packages calling `repo.delete()` directly): change `if (!result.success)` to `if (!result)` for miss handling.

#### Agent-auth helpers — DPoP + capability mandates

For AI-agent flows on protected resources (AP2 / Stripe x402 / MCP authorization). Three new helpers in `@classytic/arc/permissions`:

```typescript
import { requireAgentScope, requireMandate, requireDPoP } from '@classytic/arc/permissions';

defineResource({
  name: 'invoice',
  actions: {
    pay: {
      handler: payInvoice,
      permissions: requireAgentScope({
        capability: 'payment.charge',
        scopes: ['payment.write'],
        requireDPoP: true,                                 // RFC 9449 sender-constrained
        audience: (ctx) => `invoice:${ctx.params?.id}`,    // mandate must bind to this resource
        validateAmount: (ctx, m) => (ctx.data as { amount: number }).amount <= (m.cap ?? 0),
      }),
    },
  },
});
```

`RequestScope.service` gains optional `mandate?: Mandate` + `dpopJkt?: string` fields (additive — no breaking change). New `Mandate` type carries `id`, `capability`, `cap`, `currency`, `expiresAt`, `parent`, `audience`, `meta`. New `getMandate(scope)` / `getDPoPJkt(scope)` accessors in `@classytic/arc/scope`.

Your `authenticate` callback verifies the mandate (one `jose.jwtVerify()` call) + the DPoP proof (one `jose.dpop.verify()` call) and populates the scope. Arc validates **what's already proved** against the action being attempted — no peer-deps on `jose`, no parser embedded.

`requireDPoP()` — sender-constrained credential check. `requireMandate(capability, opts)` — capability + ttl + audience + amount validation. `requireAgentScope({ capability, scopes, requireDPoP, audience, validateAmount, noElevatedBypass })` — the composite (use this; one metadata tag downstream tools can read). Full guide → [`skills/arc/references/agent-auth.md`](../skills/arc/references/agent-auth.md).

### Unified cache layer — one plugin across kits + arc

Arc no longer maintains an aggregation-side SWR wrap. The kit's `cachePlugin` (now canonical at `@classytic/repo-core/cache`) handles every read op — `getById`, `getAll`, `aggregate`, `count`, `distinct`, `exists` — through one TanStack-shaped per-call options bag. Arc's job at the boundary is one translation: `defineAggregation({ cache: { staleTime, gcTime, swr, tags } })` → `aggReq.cache: CacheOptions` → kit handles SWR + tag invalidation + version-bump on writes.

#### Per-call shape (across CRUD + aggregate)

```ts
{
  staleTime?: number;     // seconds fresh
  gcTime?: number;        // seconds retained past stale (default 60)
  swr?: boolean;          // serve-stale + bg refresh (arc default true for aggregations)
  tags?: readonly string[];
  bypass?: boolean;       // force fresh fetch + write (Refresh button)
  enabled?: boolean;      // skip cache entirely
  key?: string;           // explicit override
}
```

#### What arc dropped

- `runWithAggregationCache` SWR wrap in `buildAggregationHandler` — replaced by passthrough to `repo.aggregate(req)`. The kit plugin's `before:aggregate` hook does the SWR work.
- Arc's `x-cache: HIT|STALE|MISS` header on aggregation routes — observability flows through the kit plugin's `log: { onHit, onStale, onMiss }` callback instead.
- The arc-side `aggregationCacheParams` / `aggregationCacheScope` helpers — scope tags auto-extract from `context.filter.organizationId` / `userId` inside the plugin (cross-tenant safety) without arc rebuilding the key.

#### What you gain

- **One Redis instance** serves the whole app — repo-bound paths (CRUD + aggregate) share keys with action results / custom routes / MCP / other framework hosts.
- **Cross-cutting tag invalidation** — `repo.cache?.invalidateByTags(['orders'])` after a write wipes both `repo.getAll(...)` AND `aggregate({ groupBy: 'status' })` if both declared the `'orders'` tag. Plus model-tag is automatic — every write to `orders` auto-invalidates anything tagged `'order'`.
- **TanStack Query-shaped vocabulary** — `staleTime` / `gcTime` / `swr` / `bypass` / `enabled` matches the React idiom devs already know. Fewer concepts.
- **`AggCacheOptions` is now a type alias for `CacheOptions`** — same shape across CRUD + aggregate. The old `ttl` / `staleWhileRevalidate` field names are removed; migrate to `staleTime` / `swr`.
- **Strictly-monotonic version bumps** — `bumpModelVersion` uses `max(Date.now(), previous + 1)` so same-millisecond writes don't collide and leak stale entries.

#### Migration

```ts
// Before (2.12 and earlier)
defineAggregation({
  cache: { staleTime: 30, gcTime: 60, tags: ['orders'] },
  ...
})
// Wired against arc's QueryCache via arcPlugins.queryCache: true.

// After (2.13) — same declaration, kit-canonical wiring
defineAggregation({
  cache: { staleTime: 30, gcTime: 60, swr: true, tags: ['orders'] },
  ...
})
// Wired by installing cachePlugin on the repo:
new Repository(model, [
  multiTenantPlugin({ tenantField: 'orgId' }),
  cachePlugin({ adapter: redisAdapter, defaults: { gcTime: 300 } }),
])
```

Hosts who don't install `cachePlugin` get a non-cached call path — declaration is harmless. Same `cache:` shape works for `getById` / `getAll` / `aggregate` / etc. via `options.cache` (CRUD) or `req.cache` (aggregate).

`arc/src/cache/QueryCache.ts` stays as the host-level cache for non-repo paths (custom routes, action results) but is no longer wired by arc onto repo-bound paths.

### Hardened — `StandardRepo.getOrCreate` returns `{ doc, created }` (cross-kit contract change)

`@classytic/repo-core` 0.4.0 originally shipped `StandardRepo.getOrCreate?(filter, data, options)` returning `Promise<TDoc | null>`. ```ts

```ts
  data: Partial<TDoc>,
  options?: WriteOptions,

```

Implementations in `@classytic/mongokit` 3.13 (`actions/read.ts` — uses `findOneAndUpdate`'s `lastErrorObject.upserted` to derive `created`) and `@classytic/sqlitekit` 0.3 (`actions/read.ts` — `created: true` on the INSERT-RETURNING path, `false` on the SELECT-hit path) both updated. ### Adoption evaluation — `claim` and `getOrCreate` in arc internals

Both new primitives were evaluated against arc's repository-backed `EventOutbox` and `IdempotencyStore`. **Neither adopted; both decisions documented in source with regression tests.**

- **Outbox** ([`src/events/repository-outbox-adapter.ts`](src/events/repository-outbox-adapter.ts)): the FIFO claim-next loop needs a *filter*, not an id, so `claim(id, ...)` would force a 2-call shape and a TOCTOU window. `acknowledge` uses a broader-than-`from` filter (`ne('status', 'delivered')`); `fail` has no source-state predicate at all. Each is intentionally more permissive than `claim`'s exact-`from` contract. Locked in by `tests/events/repository-outbox-claim-noop.test.ts`.
- **Idempotency** ([`src/idempotency/repository-idempotency-adapter.ts`](src/idempotency/repository-idempotency-adapter.ts)): `tryLock` covers TWO race-detection paths in one `findOneAndUpdate` round-trip — first-time acquire AND stale-lease takeover. `getOrCreate` definitionally cannot mutate an existing row, so it would silently fail to take over an expired lease (returning `{ doc: staleRow, created: false }`), breaking the plugin's "crashed handler eventually unblocks" guarantee. Locked in by `tests/idempotency/get-or-create-evaluation.test.ts`.

Both primitives remain valuable for hosts and future kits; arc internals just happen to do compound CAS that reaches beyond what these field-grade primitives target.

### Migration — audit TTL index (Mongo/mongokit hosts only)

Arc ≤ 2.9.0 auto-created an unnamed `timestamp_1` index on `audit_logs`. Hosts upgrading in place that declare their own `ttl_timestamp` index with `expireAfterSeconds` hit:

```
IndexOptionsConflict: Index with name: timestamp_1 already exists with different options
```

The idempotent recipe below handles both the fresh-install and upgrade-in-place cases — safe to run on every boot. It reaches directly for the Mongoose collection API because that's where indexes live on the Mongo backend:

```typescript
const indexes = await AuditModel.collection.indexes();
const legacy = indexes.find(
  (ix) => ix.name === 'timestamp_1' && ix.expireAfterSeconds === undefined,
);
if (legacy) {
  await AuditModel.collection.dropIndex('timestamp_1');
}

await AuditModel.collection.createIndex(
  { timestamp: 1 },
  {
    name: 'ttl_timestamp',
    expireAfterSeconds: 60 * 60 * 24 * 30, // 30 days — tune per retention policy
  },
);
```

SQL / sqlitekit / Prisma hosts were never affected — the auto-created index only shipped on the Mongo backend; SQL hosts own their `audit_logs` schema end-to-end via their migration tool.
