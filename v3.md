# Arc v3 — Design Notes

Internal planning doc. Not shipped in the npm package.

## Why v3

v2 proved the resource-oriented model works. But real-world usage (especially AI agents building apps) exposed friction:

- `additionalRoutes` + `wrapHandler` is confusing — agents fall back to raw Fastify
- `schemaOptions.fieldRules` is stringly-typed, no autocomplete
- Permission helpers are powerful but verbose for common cases
- `toPlugin()` is invisible to AI agents
- QueryParser config duplicates between constructor and schemaOptions

v3 keeps `defineResource()` — same config object pattern, just cleaner fields.

## Master plan — four pillars (2026-08-13)

The consolidated roadmap. It organizes everything below and in §11 into phases; items already specified elsewhere are referenced, not restated.

**What "most powerful backend framework on Fastify" means, concretely.** Not feature count — four properties, each machine-verified:

1. **Transactional truth** — a request either fully happened or didn't, and its events cannot lie about it.
2. **Declared topology** — the process knows its role and refuses work that contradicts it.
3. **One policy plane** — every surface (REST, MCP, realtime, jobs) enforces the same decisions from the same evaluator.
4. **Proven guarantees** — every "arc guarantees X" has a conformance suite a third party can run; anything unproven is documented as best-effort.

**Design invariants (already in force; every phase is judged against them):**
- One implementation per rule; mirrors are future divergences. Contracts live in primitives/repo-core, runtime in arc, drivers in kits.
- Fail-closed; boot-fatal over runtime warn over silent drop. A declaration that cannot take effect refuses to register.
- At-least-once + idempotent consumers, stated plainly. **Never promise exactly-once.**
- Enforcement code ships mutation-proven; ports ship with conformance suites; guarantees land in `wiki/delivery-guarantees.md`.
- Context budget: docs per the CLAUDE.md ownership table; no rotting metrics.

### Phase 0 — Debt that makes everything else cheaper

- **`.gitattributes` (`* text=auto`, `*.ts eol=lf` …)** — CRLF corruption bit twice in one week (mongokit `Repository.ts`, arc `defineResource/controller.ts`); a one-file fix ends the class. Apply to every classytic repo.
- **Test import cost** — the suite is import-bound (import time ≈ test time). Shared boot fixtures + trimming heavyweight imports in small files. No assertion cuts: the suite has no redundancy (measured — duplicate titles are per-subject).
- ~~**De-globalize `arcLog`**~~ — ✅ SHIPPED (unreleased): per-app `AsyncLocalStorage` scope entered for boot + request lifecycle; process global demoted to the out-of-scope fallback. **Unified retry/backoff vocabulary** (§11, blocked on repo-core) remains — a "one implementation per rule" debt.

### Phase 1 — Transactional core ⭐ (highest value)

> **Status**: 1a SHIPPED in repo-core [Unreleased] — conflict taxonomy (`isTransientConflictError` + `neverTransient` default), `VersionConflictError` + `ifVersion` CAS contract + `optimisticConcurrency` capability + conformance block, `retryingTransaction` envelope over an extended `withRetry` (maxDelayMs/jitter/abortable sleep — closing the §11 retry-vocabulary gaps). 1b SHIPPED in the kits — mongokit 3.34.0 (`transactionRetry: 'managed'`, `optimisticConcurrency: true`, `ifVersion` CAS with exclusive version-field ownership) and sqlitekit 0.9.0 (`transactionRetry: 'caller'`, `optimisticConcurrency` flipped on by a configured `versionField`) — so BOTH retry owners are real and the envelope can be exercised against each. The UnitOfWork port was analysed and dropped (see below). **1c — arc's request envelope + `ctx.uow` — is therefore UNBLOCKED; it was never waiting on repo-core.**

A handler that writes twice and fails between the writes leaves partial state, and a concurrent-write conflict has no retry answer — cleanup-after-the-fact (outbox, compensation) is weaker than atomicity. Arc has the *pieces* — `runInTransaction()` ALS (2.18), `OutboxStore.transactionalSave` (primitives 0.18), write-verb contexts — but no envelope composing them. Close it as ONE design, not four flags:

- ~~**UnitOfWork port** (repo-core): `begin/commit/rollback`~~ — ❌ **NOT BUILDING. Analysed 2026-08-23; the port already exists under another name.**
  - The **taxonomy** half shipped in 1a (`isTransientConflictError` + `neverTransient`, per-kit mapping, conformance-tested). Nothing outstanding.
  - The **scope** half is `withTransaction(fn, uow?)`. Its callback parameter is *literally named `uow`*, and `TransactionHandle` is already documented as the join point for work outside the repository (`outbox.store(event, { session: uow.session })`). `retryingTransaction` is the bounded-retry envelope over it.
  - **An imperative `begin/commit/rollback` cannot express `transactionRetry: 'managed'`.** Mongo's `session.withTransaction()` owns re-invocation of a CALLBACK; with no callback there is nothing for the driver to re-run. Adding the imperative port would either regress the double-retry defect 0.23.0 fixed, or be unimplementable on mongokit — the primary kit.
  - It would also be a second spelling of "transaction" in repo-core, against its own *one implementation per rule* invariant, and strictly less safe: a caller can forget to commit, a scope cannot leak.
  - **Consequence: repo-core needs nothing further for Phase 1.** `ctx.uow` is an ARC-level composition — repo-core owns the driver join point (`session`); the outbox writer, actor/tenant, trace, and idempotency record are arc's to assemble around it.
- **Request envelope** (arc): `defineResource({ transactional: true })` or app default → begin → pipeline → handler/verb → **outbox rows written in-session** → commit → relay tick. ✅ The envelope itself (`runWritePersistence` over `retryingTransaction`), `ctx.uow` on write verbs, AND ambient-session publication (`transactionContext`, so audit/outbox/idempotency join the transaction) are SHIPPED (unreleased). ✅ Outbox rows now write in-session by DEFAULT (`createOutboxModule` defaults `sessionProvider` to the ambient `transactionContext`), so the durable path needs no host discipline. **Remaining: an app-level `transactional` default, and routing arc's AUTOMATIC CRUD events through the outbox** — the latter is a seam-PLACEMENT change, not a wiring one: the publisher is an `after('*', op)` hook and after-hooks run post-commit by design, which is what makes conflict re-run safe. Moving it inside the transaction would re-run every publish on each retry. It needs its own design (in-transaction event write + suppressing the post-commit publish when an outbox owns the resource), not a flag. On retryable conflict: rollback, jittered backoff, bounded re-run. Re-run is safe **by construction**, not by convention: side effects are outbox-deferred, after-hooks run once post-commit, before/around hooks are documented pure-or-idempotent.
- **`ctx.uow`** on write verbs and handlers: session, outbox writer, actor/tenant, trace, idempotency record — one context object per request, and the **transactional idempotency seam** (§11) lands inside it rather than as its own feature.
- **Optimistic concurrency**: repo-core `WriteOptions.ifVersion` + `VersionConflictError`; kits implement CAS; arc maps to HTTP 409 + ETag/`If-Match`. Opt-in per resource (`concurrency: 'optimistic'`). Arc currently has NO answer to write-write conflicts; this is the smallest correct one.
- ~~**Route automatic CRUD events through the outbox**~~ — ❌ **NOT BUILDING. Analysed 2026-08-23.**
  - The item was written against `eventStrategy`, which **does not exist in `src/`** — it appears only in docs (now corrected). The real gate is `emitEvents: boolean` on `arcCorePlugin`. Building this would mean inventing the feature first.
  - Automatic CRUD events are DERIVED notifications: `{ resource, operation, data, userId, timestamp }`. The row is the source of truth, so a consumer that misses one can re-read it. The events that must not be lost (`order.paid`, `invoice.issued`) are domain events a host publishes deliberately — and those now join the transaction with ZERO wiring (`createOutboxModule` defaults `sessionProvider` to the ambient `transactionContext`).
  - The cost lands on every mutation — an outbox row plus relay delivery per write, heaviest on the highest-write resources, for events most consumers ignore.
  - It needs a suppression rule ("when an outbox owns the resource, skip the post-commit publish") or consumers get everything twice — a conditional dual-path, against this document's own *one implementation per rule*.
  - **The real risk is a false BELIEF, not a missing guarantee**: a host builds a workflow on `product.created` assuming delivery, when publishing is fire-and-forget (`failOpen: true`). The answer to a false belief is to STATE the guarantee, not upgrade it. Replacement item below.
- **Disclose the CRUD-event guarantee** (small): when `emitEvents` is on AND an outbox module is registered — a host who has demonstrably bought into durability — say plainly that automatic CRUD events do not use the outbox, and name the durable path. Uses the existing duplicate-publish-warn / runtime-capability-audit precedents. Costs nothing per write.

### Phase 2 — Declared topology

- ~~**`createApp({ role })`**~~ — ✅ SHIPPED (`CreateAppOptions.role`, `src/factory/types/app-options.ts`). `'api' | 'worker' | 'relay' | 'scheduler' | 'all'` (default `'all'`, the previous behaviour). The matrix decides what mounts: api = HTTP + dispatch, no consume/relay/schedule ticks; relay = outbox only; scheduler = schedule leadership. Contradictions are boot-fatal (a `role: 'relay'` app declaring routes refuses to start). `jobsPlugin({ mode: 'producer' | 'worker' | 'both' })` falls out of the same axis.
  **Implementation spec (pinned 2026-08-13; wiring points verified in source):**
  - Option: `CreateAppOptions.role` (`src/factory/types/app-options.ts`, beside `runtime`). Default `'all'`.
  - Enforcement points, all existing seams:
    1. **jobs** — `role: 'api'` threads `mode: 'producer'` into `jobsPlugin` (shipped: `e211d00`); `'worker'` threads `mode: 'worker'`; explicit `jobsPlugin.mode` wins.
    2. **schedules** — `role: 'api' | 'worker' | 'relay'` skips `schedulesPlugin` tick registration (`registerArcPlugins`); `'scheduler'`/`'all'` runs it. Module `scheduledJobs` arms (incl. the outbox module's relay arm) follow the same gate — the relay arm is a schedule, so `'relay'` runs ONLY outbox-named schedule arms, which needs an arm tag: `ScheduleDefinition.kind?: 'relay' | 'job'` (additive).
    3. **HTTP** — `role: 'relay' | 'scheduler'` with declared `resources`/`routes` is BOOT-FATAL (contradiction, not a warning); `role: 'worker'` allows routes (Optional per the matrix).
    4. **Boot audit line** — one info log stating role + what mounted/skipped, so a misdeployed process is legible from its first log line.
  - Tests: contradiction boot-throws; role 'api' app registers zero Workers + zero schedule ticks; 'relay' runs only relay arms; default byte-identical. Mutation: flip each gate.
  - NOT in this slice: capability registry (separate item), fencing, webhook durability.

- ~~**Runtime capability registry** (§11) is the enforcement floor under `role`~~ — ✅ SHIPPED alongside it; one boot audit replaced the "validate what createApp can see + wiki checklist" split.
- **Fencing tokens** (§11): lease acquisition returns a monotonic token (repo-core `LockAdapter` + primitives `OutboxStore` evolution); stores that can verify it reject stale writers; stores that can't are documented in the matrix. Coordinate with kits — ecosystem change.
  **Fencing spec (pinned 2026-08-13; wiring points verified):**
  - repo-core `LockAdapter.acquire` → returns `{ acquired: boolean; token?: number }` (additive: boolean-returning adapters stay valid; token-aware callers feature-detect). Token = monotonic per lock name, minted by the STORE (not the process — a process cannot fence itself).
  - primitives `OutboxStore`: `claim` results gain `fencingToken?`; `acknowledge`/`fail` accept `{ fencingToken? }` and stores that persist a per-row token REJECT a stale one (`OutboxOwnershipError`). Conformance: expired-lease takeover mints a HIGHER token; the old holder's ack with the old token throws.
  - arc: `EventOutbox` threads the token through relay → ack/fail untouched (feature-detected, like `session`). Schedules: `LockAdapter` token logged on acquire so overlap forensics have a number to compare.
  - Kits: mongokit outbox store = `$inc` a `fenceSeq` on the lease doc at claim; sqlitekit = `version`-column bump. Both are the SAME CAS shape as `ifVersion` — reuse, don't hand-roll.
  - Stores that cannot fence (pure memory) declare it; the matrix documents which do.

- ~~**Durable webhook delivery** (§11)~~ — ✅ SHIPPED; outbox → worker composition, no new subsystem.

### Phase 3 — One policy plane

- **Declarative row policies** — `PolicyRule { resource, operation, subject-predicate, filter }` where `filter` is the **portable Filter IR arc already compiles per-kit**. Stored behind a `PolicyStore` port (host DB), versioned + cache-invalidated, feeding the SAME PDP (`evaluatePermissionDecision`) and composing with code-first checks by AND — a stored rule can only *narrow*, never widen. Deployments adjust policy without a release; code stays the floor.
- **Admission control** (§11): one `pressure` module — ELU, DB pool (kit seam), queue depth, oldest-outbox age — feeding one policy: 429 for tenant quota, 503 for saturation, readiness flips, worker-concurrency reduction. Replaces scattered under-pressure knobs. Rate limiting bounds request *frequency*; this bounds concurrent *expensive work* — different axis, one module.

### Phase 4 — Convergence & proof

- **QueryCache → repo-core `CacheEngine` façade** (§11 — already decided; needs its conformance wave).
- **Conformance completion** — the scenarios no suite yet pins: crash-recovery replay, expired-lease takeover + fencing, duplicate-delivery idempotency, DLQ replay round-trip, transaction rollback leaving no orphans. Each lands in the relevant `@classytic/arc/testing/*` contract.
- **Repeatable benchmark lane + `arc doctor` index checks + streaming multipart** (§11). Scale claims stay out of the README until the lane exists.
- **Reference architecture page** — outbox → broker → worker, single-node (declared memory + repo outbox) through Level 3 distributed; one wiki page, replacing scattered guidance.

### Non-goals — declared so they stay closed

No ORM (kits own data). No UI/views/reports. No workflow engine (`@classytic/streamline` owns that). No multi-region consensus — tenant-affine regional ownership is documented guidance, not a runtime. No exactly-once, ever. No CPU scheduling — heavy work exits the API process via jobs. No driver-aware config shorthand (`model: Model` and friends): arc has shipped zero kit-specific adapters since 2.12 and `check:boundaries` forbids a driver import, so the adapter stays the seam. No v2 compatibility layer — see the compatibility policy.

### Sequencing

Per the 2026-07-21 policy, everything above lands in ⚠-marked **minors** in phase order — v3 the version stays reserved for the API rewrites (§1–§2) and the Fastify 6 / Node 24 baseline, which Phase 1–4 must not wait for. Each phase is independently shippable and gate-verified before the next starts.

## Platform baseline — Fastify 6 + Node.js 24

Arc v3 is the Fastify 6 generation of the framework:

- `fastify: ^6.0.0` is the required peer dependency. Arc v3 does not support
  Fastify 5 at runtime; applications that must remain on Fastify 5 stay on Arc
  v2.
- Node.js 24 is the minimum supported runtime, matching Fastify 6's published
  support matrix. Arc may use Node 24 APIs directly and does not ship runtime
  ponyfills for older Node releases.
- The implementation and compatibility work may track Fastify 6 prereleases,
  but Arc v3 must not publish stable against a Fastify alpha, beta, or release
  candidate. The stable release is gated on Fastify 6 stable and compatible
  releases of Arc's required `@fastify/*` plugins.
- Fastify remains a peer dependency and is never bundled. There must be one
  host-resolved Fastify major so plugin encapsulation, decorators, hooks, and
  declaration merging all operate on the same instance and type universe.

This is an intentional major-version boundary, not a transparent dependency
bump. Fastify 6 removes APIs deprecated in v5 and changes several boot-time
defaults. Arc v3 absorbs those changes in `createApp()` where it owns the
configuration and exposes clear migration errors where the host owns it.

### Fastify 6 changes Arc must adopt

1. **Router options are nested.** `querystringParser`, `caseSensitive`,
   `allowUnsafeRegex`, `constraints`, `ignoreTrailingSlash`,
   `ignoreDuplicateSlashes`, `maxParamLength`, and `useSemicolonDelimiter`
   belong under `routerOptions`. Arc's public factory types use the Fastify 6
   shape and its internals never forward these as top-level Fastify options.
2. **Error-handler overrides fail closed.** Fastify 6 defaults
   `allowErrorHandlerOverride` to `false`. Arc keeps that default, registers one
   error handler per encapsulation scope, and does not turn the legacy behavior
   back on globally. A host that deliberately replaces a handler must opt in
   explicitly and own the consequences.
3. **Logging configuration uses `logController`.** The removed top-level
   `disableRequestLogging` and `requestIdLogLabel` options are represented via a
   Fastify `LogController`. Arc's logger integration must compose with a
   host-provided controller rather than silently replace it.
4. **HTTP method replacement is explicit.** Calling `addHttpMethod()` for an
   existing method requires `{ overrideExisting: true }`. Arc must never rely
   on the Fastify 5 warning-and-continue behavior.
5. **Removed type aliases stay removed.** Arc source and declarations use
   `FastifyPluginAsync` / `FastifyPluginCallback`, `FastifyBaseLogger`,
   `FastifySchemaValidationError`, `request.raw`, and
   `request.routeOptions`. They do not re-export compatibility aliases for
   `FastifyPlugin`, `FastifyLoggerInstance`, `ValidationResult`,
   `FastifyRequestContext`, `FastifyReplyContext`, `ResSerializerReply`, or
   `request.req`.
6. **Error-code consumers migrate.** Code matching
   `FST_ERR_INSTANCE_ALREADY_LISTENING` uses
   `FST_ERR_INSTANCE_ALREADY_STARTED`. Arc should avoid coupling public
   behavior to Fastify-private messages; match documented error codes only
   where integration behavior genuinely requires it.

### Compatibility policy

- Arc v2 receives Fastify 5 compatibility and security fixes; it does not grow
  a partial Fastify 6 compatibility mode.
- Arc v3 tests only Fastify 6. A dual-major peer range such as
  `>=5 <7` is forbidden because it advertises combinations the release lane
  cannot prove.
- Every Arc-owned Fastify plugin entry declares Fastify 6 compatibility through
  `fastify-plugin` metadata. Ecosystem plugins must publish a Fastify 6-compatible
  major before being listed as v3-compatible.
- The v3 CI matrix includes Node 24 on Linux and the supported Windows/macOS
  lanes, type tests against the minimum supported Fastify 6 release, and a
  second lane against the newest compatible Fastify 6 release.
- Fastify prereleases are useful as a non-blocking forward-compatibility lane
  while v3 is in development; they are never admitted by the stable peer range.
- **No backward-compatibility layer, anywhere.** v3 carries no deprecated
  fields, no aliases, no accepted-with-a-warning shapes, and no v2 emulation.
  A removed or renamed surface fails the boot with a message naming its
  replacement. v3 is designed as if v2 did not exist; the codemod
  (`npx @classytic/arc migrate v2-to-v3`) is the only migration aid.
- **One way to do each thing.** Where v2 accumulated two spellings of the same
  capability, v3 ships the better one and deletes the other. Two affordances
  survive together only when they do genuinely different jobs (e.g.
  `createApp({ resources })` composes an arc app, while `toPlugin()` mounts
  resources into a Fastify app the host owns) — never as a courtesy to
  existing code.

### Breaking defaults + renames committed for v3

Each of these ships as documentation or a warning in 2.x — the behaviour change waits for the major.

**`strictPermissions` becomes the default.** An omitted CRUD permission currently mounts the route with NO permission middleware and only warns, so a resource can ship an unauthenticated write by omission — the asymmetry that made `permissions: readOnly()` a real incident before 2.20. v3 flips the default: an ungated WRITE fails the boot, and `strictPermissions: false` becomes the explicit opt-out for hosts that genuinely want public writes. 2.x behaviour is unchanged; the boot warning now names `ARC_STRICT_PERMISSIONS=true` as the production posture so hosts can adopt early and land on v3 with nothing to change.

**`ArcModule.plugins` → `setup`.** The slot is a setup function arc CALLS; it is never passed to `fastify.register()`, so there is no encapsulation and no prefix, and a module author must register plugins themselves. The name invites exactly the wrong mental model. v3 renames it to `setup`, and `plugins` is REMOVED — a module declaring it fails boot with a message naming the new field, not a warning that can be filtered. In 2.x the JSDoc states the semantics prominently and the two failure modes the name invites are detected at boot: returning a `fastify-plugin` throws, and returning a multi-argument function warns (arc calls disposers with zero arguments).

## 1. Cleaner defineResource()

### Problem
v2 leaks internals (`_appliedPresets`, `wrapHandler`), duplicates config, and has unintuitive names.

### v3 Design

```typescript
import { defineResource, field, public, auth, roles, owner } from '@classytic/arc';

const product = defineResource({
  name: 'product',
  model: ProductModel,                          // auto-detects adapter (MongoKit/Prisma/custom)

  fields: {
    name: field.string().required(),
    price: field.number().min(0),
    category: field.enum('electronics', 'books', 'food'),
    internalScore: field.number().hidden(),
    createdAt: field.date().readonly(),
  },

  filter: ['category', 'status'],               // single source of truth (no more dual config)
  sort: ['createdAt', 'price'],
  operators: ['gte', 'lte', 'in', 'ne'],

  permissions: {
    list: public(),
    get: public(),
    create: roles('admin', 'editor'),
    update: owner('createdBy'),
    delete: roles('admin'),
  },

  presets: ['softDelete'],

  routes: [
    { method: 'POST', path: '/approve', handler: 'approve' },
    { method: 'POST', path: '/webhook', handler: webhookFn, raw: true },
    { method: 'GET', path: '/trending', handler: trendingFn, mcp: true },
  ],
});
```

**What changed from v2:**

| v2 | v3 | Why |
|----|-----|-----|
| `adapter: createMongooseAdapter(...)` | `model: ProductModel` | Auto-detect, zero boilerplate |
| `schemaOptions.fieldRules: { name: { type: 'string' } }` | `fields: { name: field.string() }` | Type-safe, autocomplete, no typos |
| `schemaOptions.filterableFields` + `QueryParser({ allowedFilterFields })` | `filter: [...]` | Single source of truth |
| `additionalRoutes: [{ wrapHandler: true }]` | `routes: [{ handler: 'methodName' }]` | Clear naming, no boolean confusion |
| `permissions: { list: allowPublic() }` | `permissions: { list: public() }` | Shorter, same function |

### What stays the same
- `defineResource()` returns `ResourceDefinition` (same internal type)
- Config object pattern (no builder)
- Field SEMANTICS carry over unchanged wherever a field survives — v3 renames
  and removes fields, it does not redefine the ones it keeps
- Same BaseController, same pipeline, same adapters internally

## 2. routes + actions — Unified DX

### Problem
v2 has three separate concepts for "adding behavior to a resource":
- `additionalRoutes` + `wrapHandler: true/false` — confusing boolean
- `onRegister` + `createActionRouter` — exposes Fastify internals
- Raw Fastify plugins — users give up and bypass Arc entirely

AI agents (Claude, Cursor) can't figure out the pattern and write bad code.

### v3 Design: Two Configs, Zero Fastify

**`routes`** — custom endpoints (GET /stats, POST /export, POST /webhook):

```typescript
routes: [
  // String handler = controller method → full pipeline + MCP tool
  { method: 'GET', path: '/stats', handler: 'getStats' },

  // Function handler = inline → full pipeline + MCP tool
  { method: 'GET', path: '/export', handler: async (ctx) => ({ url: buildExportUrl() }) },

  // raw: true = raw Fastify handler → no pipeline, no MCP
  { method: 'POST', path: '/webhook', handler: webhookFn, raw: true },

  // Explicit MCP + permissions
  { method: 'POST', path: '/fulfill', handler: 'fulfill',
    permissions: roles('warehouse-manager'),
    mcp: { description: 'Fulfill this order', annotations: { destructiveHint: true } },
  },
]
```

**`actions`** — state transitions → unified `POST /:id/action` endpoint:

```typescript
actions: {
  approve: async (id, data, req) => transferService.approve(id, req.user._id),
  dispatch: {
    handler: async (id, data, req) => transferService.dispatch(id, data.transport, req.user._id),
    permissions: roles('warehouse-staff'),
    schema: { transport: { type: 'object' } },
    mcp: { description: 'Dispatch transfer to destination' },
  },
  cancel: {
    handler: async (id, data, req) => transferService.cancel(id, data.reason, req.user._id),
    permissions: roles('admin'),
    schema: { reason: { type: 'string', minLength: 10 } },
  },
},
actionPermissions: auth(),  // fallback for actions without per-action permissions
```

### Why `actions` is separate from `routes`

Actions are NOT individual HTTP endpoints. They share a **single** `POST /:id/action` endpoint with `{ action: 'approve', ...data }`. This is the Stripe pattern — proven in production (transfers, invoices, orders).

Putting actions in `routes` would require a merge syntax for "these 5 entries become one HTTP route." That's more confusing, not less.

### Rules

**Routes:**
- `handler: 'string'` → controller method → full pipeline + MCP tool
- `handler: function` → inline → full pipeline + MCP tool
- `raw: true` → raw Fastify, no pipeline. `mcpHandler` for parallel MCP entry.
- `permissions` required (no accidental public exposure)
- `mcp: false` to skip MCP tool generation

**Actions:**
- Bare function = shorthand handler (uses `actionPermissions` fallback)
- Object = full config (handler + permissions + schema + mcp)
- Per-action permissions override `actionPermissions`
- Each action = one MCP tool: `{action}_{resource}` (e.g. `approve_transfer`)
- Schema fields become MCP tool input alongside `id`

### Full Example: Invoice Resource

```typescript
const invoice = defineResource({
  name: 'invoice',
  model: InvoiceModel,
  
  fields: {
    number: field.string().required().readonly(),
    status: field.enum('draft', 'posted', 'paid', 'cancelled').default('draft'),
    total: field.number().readonly(),
    dueDate: field.date(),
  },

  filter: ['status', 'customer', 'dueDate'],
  sort: ['createdAt', 'dueDate', 'total'],

  permissions: {
    list: auth(),
    get: auth(),
    create: roles('accountant', 'admin'),
    update: roles('accountant', 'admin'),
    delete: roles('admin'),
  },

  routes: [
    { method: 'GET', path: '/aging', handler: 'getAgingReport',
      summary: 'Aging report (AR/AP)' },
    { method: 'GET', path: '/overdue', handler: 'getOverdue' },
    { method: 'POST', path: '/receipt', handler: 'generateReceipt',
      permissions: roles('accountant', 'admin') },
    { method: 'GET', path: '/:id/document', handler: 'getDocument',
      mcp: false },  // PDF download doesn't make sense as MCP tool
    { method: 'POST', path: '/batch/post', handler: 'batchPost',
      permissions: roles('accountant', 'admin') },
  ],

  actions: {
    post: {
      handler: async (id, data, req) => invoiceService.post(id, req.user),
      permissions: roles('accountant', 'admin'),
      description: 'Post invoice to general ledger',
    },
    cancel: {
      handler: async (id, data, req) => invoiceService.cancel(id, data.reason, req.user),
      permissions: roles('accountant', 'admin'),
      schema: { reason: { type: 'string', minLength: 5 } },
    },
    void: {
      handler: async (id, data, req) => invoiceService.void(id, req.user),
      permissions: roles('admin'),
      mcp: { annotations: { destructiveHint: true } },
    },
    record_payment: {
      handler: async (id, data, req) => invoiceService.recordPayment(id, data, req.user),
      permissions: roles('accountant', 'admin'),
      schema: {
        amount: { type: 'number', minimum: 0.01 },
        method: { type: 'string', enum: ['cash', 'bank_transfer', 'credit_card'] },
        reference: { type: 'string' },
      },
    },
  },
  actionPermissions: auth(),

  presets: ['softDelete', 'audited'],
});
```

**MCP tools auto-generated:** 5 CRUD + 4 routes + 4 actions = **13 tools from one config**.

### Validation (fail-fast at define time)

- Action name cannot match CRUD operation (`create`, `update`, `delete`, `list`, `get`)
- Route path `/:id/action` conflicts with `actions` config → error
- `permissions` required on all routes (no accidental public exposure)
- Action handler must be a function

### What's gone

| v2 | v3 | Status |
|----|-----|--------|
| `additionalRoutes` | `routes` | Removed |
| `wrapHandler: true/false` | `handler: string` vs `raw: true` | Removed |
| `onRegister` for actions | `actions` config | `onRegister` survives as the raw-Fastify escape hatch — a different job, not a compat path |
| `createActionRouter()` import | `actions` config | Survives for mounting actions WITHOUT a resource — a different job, not a compat path |

## 3–8. Decided & closed

One line each, kept ONLY so a settled question is not re-opened. Detail lives in
[changelog/v2.md](changelog/v2.md) and git history — this is not an archive.

**Dropped — do not re-propose**
- **Unified query config** — already solved in 2.7.x: `filterableFields` auto-derives from `QueryParser.allowedFilterFields`, so there is no duplication left to unify.
- **Type-safe field builders** (`field.string()`) — a factory returning `{ type: 'string' }`. `fieldRules` types already give autocomplete; a parallel API buys surface, not safety. Improve `FieldRuleEntry` instead.
- **Auto-detect adapter** — inferring the kit from a model object makes the wiring implicit and the failure mode ("wrong kit chosen silently") worse than the explicit call it replaces.
- **Permission shorthand** (`allowPublic()` → `public()`) — saves five characters, costs an export plus migration confusion.
- **App-level MCP config** — moves config without simplifying it; the host still needs `overrides` / `exclude` / `extraTools` / `instructions`.

**Shipped — no longer v3 scope**
- **Registration without `toPlugin()`** — `createApp({ resources })` + `loadResources()` auto-discovery, v2.5.2.
- **Adapter split** — kit adapters moved to `@classytic/<kit>/adapter`, contracts to `@classytic/repo-core/adapter`, v2.12.0.

## 10. Migration

| v2 | v3 | Breaking? |
|----|-----|-----------|
| Fastify 5 | Fastify 6 | **Yes — framework peer major** |
| Node.js 22+ | Node.js 24+ | **Yes — runtime floor** |
| top-level Fastify router options | `routerOptions: { ... }` | **Yes — Fastify 6 rejects removed top-level options** |
| `disableRequestLogging` / `requestIdLogLabel` | `logController` | **Yes — removed by Fastify 6** |
| repeated `setErrorHandler()` in one scope | one handler, or explicit `allowErrorHandlerOverride: true` | **Yes — default now throws** |
| deprecated Fastify type aliases | Fastify 6 replacement types | **Yes — aliases removed** |
| `additionalRoutes` | `routes` | **Yes — removed** |
| `wrapHandler: true` | `handler: 'methodName'` | **Yes — removed** |
| `wrapHandler: false` | `raw: true` | **Yes — removed** |
| `schemaOptions.fieldRules` | `fields: { ... }` | **Yes — removed** |
| `filterableFields` + `QueryParser` | `filter: [...]` | **Yes — removed** |
| `allowPublic()` | `publicAccess()` | **Yes — renamed.** NOT `public()`: it is a strict-mode reserved word, so `export function public()` is a SyntaxError and `import { public }` will not parse — the name is unusable in ESM |

**v3 ships NO deprecation layer.** A removed or renamed field fails the boot
with a message naming its replacement — it is never accepted-with-a-warning.

This is the cheap choice precisely BECAUSE v3 already breaks: the Fastify peer
and Node runtime floors move, so every host must open its codebase regardless.
An alias kept "for one major" buys nothing in that world and costs permanently
— two code paths through every resolver, two shapes in every test matrix, and
documentation that must describe both until someone is brave enough to delete
one. Warnings are also the wrong instrument for a migration that is mechanical:
they are filtered, they accumulate, and they let a half-migrated codebase run
indefinitely. A boot failure naming the replacement is finished in one pass.

The codemod, not an alias layer, is the compatibility story — it rewrites the
mechanical Arc and Fastify configuration changes:

```bash
npx @classytic/arc migrate v2-to-v3
```

The codemod cannot safely decide error-handler ownership or custom
`LogController` composition. It reports those locations for manual review.

## 11. Deferred from v2.5 (Candidate for v3)

### wrapHandler + additionalRoutes → routes + actions

### bulk preset validation
Fail at registration time if the repository doesn't have `createMany`/`updateMany`/`deleteMany` instead of failing at request time.

### MCP SDK v2 migration

Schema: raw shapes → `z.object()` required. Handler context: `extra` → `ctx.mcpReq`. See `src/integrations/mcp/MIGRATION-V2.md` for exact diffs — 5 source files, mechanical changes.

### Node.js 24+ only
Drop Node 22 with the Fastify 5 baseline. Arc v3 follows Fastify 6's Node 24
minimum; see **Platform baseline — Fastify 6 + Node.js 24** above.

### NOT v3-gated — approved for the next minors (policy 2026-07-21)

**Policy: arc's user base is small, so breaking changes land in MINOR releases** with ⚠ changelog markers and migration notes — nothing below waits for a major. v3 remains the horizon for architectural rewrites only (sections above). Everything in the next three subsections is 2.25+ work, ordered by readiness, not by semver ceremony.

#### Distributed-architecture items (wave-5 audit; land as designed, no major required)

Structural work the 2.24 hardening deliberately did NOT half-build — each needs a real design, not an option flag:

- ~~**Runtime capability registry**~~ — ✅ SHIPPED (`declareRuntimeCapability`, `src/utils/runtimeCapabilities.ts`; boot audit enforces it).
- ~~**Durable webhook delivery**~~ — ✅ SHIPPED as predicted: outbox → worker composition (`createDurableWebhookModule`, `src/integrations/webhooks.ts`), deterministic row id per (event × subscription).
- **Admission control primitives** — per-resource concurrency limits, queue-depth shed, readiness driven by pool/backlog metrics. Rate limiting bounds request frequency, not concurrent expensive work; under-pressure sheds on event-loop lag only.
- ~~**De-globalize the arc logger**~~ — ✅ SHIPPED (unreleased). Resolves from the app/request scope; process global kept as the out-of-scope fallback exactly as specified.
- **Circuit breaker rolling window** — failure-RATE over a sliding window as an alternative to consecutive-failure counting (2.24 added half-open fencing + abort propagation; window strategy is additive API surface).
- **Transactional idempotency seam** — NOT a `sessionProvider` default, despite the resemblance to audit/outbox. The record is written at **`preSerialization`** (`src/idempotency/idempotencyPlugin.ts`), i.e. after the handler returned and the transaction already committed, so an ambient session would resolve to `undefined` and the default would be decoration. This is the SAME seam-PLACEMENT problem as automatic CRUD events: making it transactional means relocating the record write inside the handler's transaction, which also changes what a rollback means (record vanishes → a retry re-executes). Needs its own design.

#### repo-core convergence (wave-6/7 audits; no major required — CacheEngine façade is the big one)

- **QueryCache → repo-core `CacheEngine` façade** — repo-core's engine explicitly supersedes arc's independent cache stack (single-flight miss protection, per-scope invalidation, TTL jitter, shared tag indexing, canonical serialization). Keep `fastify.queryCache` + the resource-facing API as a compatibility façade delegating to `CacheEngine`; arc's own adapters/keys/SWR envelope go away with it (breaking is fine in a minor per policy — the reason this is 2.25 rather than "now" is that it's a focused rewrite needing its own conformance wave, not semver). Until then: **no new cache functionality in arc's implementation** unless required for compatibility. 2.24 took the prerequisite step: `CacheStore extends CacheAdapter`, signatures + TTL-on-create semantics aligned, conformance-tested against repo-core's reference adapter.
- **Unified retry/backoff vocabulary** — one canonical backoff-policy + abortable-delay primitive shared by event retry, outbox, and Streams polling (each keeps its own orchestration — DLQ routing and poll pacing are different concerns). BLOCKED on repo-core's retry primitive first gaining `maxDelayMs`, jitter, an abortable timer, and a safe default `shouldRetry` (its current retry-every-error default is unsafe to adopt broadly).
- **Migration state machine** — persist `running → applied/failed` records (operator-diagnosable dirty state), optional transactional `record()`, artifact-based checksums (Function.toString is transpile-sensitive; 2.24 defaults mismatch to warn for exactly this reason). Lease renewal landed in 2.24 (wave 7). Document expand/migrate/contract as the production rollback strategy — `down()` is an emergency tool.
- ~~**Fencing tokens — schedules + migrations**~~ — ✅ SHIPPED (unreleased): `startRenewingLease` fences via `tryAcquireFenced` and treats a token CHANGE as loss, closing the expired-interloper hole plain renewal cannot see. Arc surfaces `lease.token` for stores that accept one; it does NOT reject on their behalf — only the store holding the data can. Original note follows.
- ~~Superseded:~~ The repo-core `LockAdapter` evolution SHIPPED (`tryAcquireFenced`, 0.23.0) and arc fences the OUTBOX relay (`claimPendingFenced`) and cleanup service today. Schedules and migrations still rely on serialized lease renewal alone, which narrows the overlap window but cannot stop a STALE holder committing after lease loss. The primitive is in place — this is now arc-side wiring, not an ecosystem change.
- **`withDeadline` / `withObserverTimeout` split** — standardize the two timeout concepts (cancellable work vs work that can only be abandoned) across cache timeouts, breaker, jobs, health; 2.24 wired AbortSignals into jobs + health + breaker as the groundwork.

#### Performance/scale items (wave-12 audit; staged, not half-built in 2.24)

2.24 shipped the in-code fixes (load-shedding defaults, cache single-flight, multipart total cap, two-phase outbox claim, Streams `processingConcurrency`, WS head-pointer drain, bucketed metrics). What remains is infrastructure, each needing its own design:

- **Repeatable benchmark lane** — autocannon HTTP profiles (CRUD hot path, cached list, WS fan-out) + queue-throughput runs (outbox relay, Streams consumer) with recorded p50/p95/p99, RSS, and ELU budgets; regression-gated like `test:ci`, run pre-release rather than per-PR. Extreme-scale claims stay out of the README until this exists.
- **`arc doctor` query/index checks** — DB performance is host/kit-dependent (finding 7): doctor should surface unindexed filter/sort fields used by `defineResource` list configs, missing outbox claim indexes (`status+visibleAt+createdAt`), and tenant-field index coverage, via kit-provided introspection seams — arc stays DB-agnostic.
- **Streaming multipart primitive** — a stream-through path (busboy part → object-storage write) so large uploads never buffer in process memory; pairs with the existing presigned-URL guidance. The buffered `multipartBody()` stays the small-upload default.
