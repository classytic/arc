# Arc Handler Patterns Guide

Arc supports two patterns for writing route handlers. Choose based on your needs.

## Pattern 1: Arc Context Pattern (Recommended for most cases)

**Use when**: Standard CRUD operations, business logic, most API endpoints

**Signature**: `async methodName(req: IRequestContext): Promise<IControllerResponse>`

**Benefits**:
- ✅ Framework-agnostic (can switch from Fastify to Express)
- ✅ Clean, predictable API
- ✅ Built-in field masking, security features
- ✅ Easier to test (mock plain objects)

### Example: Standard API Endpoint

```typescript
import { BaseController } from '@classytic/arc';
import type { IRequestContext, IControllerResponse } from '@classytic/arc';

class ProductController extends BaseController {
  async getByCategory(req: IRequestContext): Promise<IControllerResponse> {
    const { category } = req.params;
    const { limit = 10 } = req.query;

    const products = await this.repository.getAll({
      filters: { category },
      limit: Number(limit),
    });

    return {
      success: true,
      data: products,
      status: 200,
    };
  }
}

// Resource definition
defineResource({
  name: 'product',
  controller: new ProductController(productRepository),
  routes: [
    {
      method: 'GET',
      path: '/category/:category',
      handler: 'getByCategory',
      permissions: allowPublic(),
      // (`handler` — not `rawHandler` — so arc wraps it in its pipeline)
    },
  ],
});
```

### Available Fields in `req: IRequestContext`

```typescript
{
  params: Record<string, string>;        // Route params: /users/:id
  query: Record<string, unknown>;        // Query string: ?page=1&limit=10
  body: unknown;                         // Request body (POST/PATCH/PUT)
  user: UserBase | null;                 // Authenticated user (or null)
  headers: Record<string, string | undefined>;  // Request headers
  organizationId?: string;               // Tenant/org ID (multi-tenant apps)
  metadata?: Record<string, unknown>;    // Custom data, hooks, policy filters
}
```

### Available Fields in Response

```typescript
{
  success: boolean;                      // true/false
  data?: T;                              // Response payload
  error?: string;                        // Error message
  status?: number;                       // HTTP status (default: 200/400)
  meta?: Record<string, unknown>;        // Pagination, counts, etc.
  details?: Record<string, unknown>;     // Debug info
}
```

## Pattern 2: Native Fastify Pattern (For special cases)

**Use when**:
- File downloads/uploads
- Streaming responses
- Custom headers (Content-Type, Cache-Control, etc.)
- Redirects
- Raw responses (HTML, XML, binary)
- WebSocket upgrades

**Signature**: `async methodName(request: FastifyRequest, reply: FastifyReply): Promise<void>`

**Benefits**:
- ✅ Full control over response
- ✅ Direct access to Fastify features
- ✅ Streaming support
- ✅ Custom content types

### Example 1: File Download with Custom Headers

```typescript
import type { FastifyRequest, FastifyReply } from 'fastify';
import { defineResource } from '@classytic/arc';
import fs from 'fs/promises';

class ReportController {
  async downloadPDF(request: FastifyRequest, reply: FastifyReply): Promise<void> {
    const { id } = request.params as { id: string };

    // Get file from storage
    const report = await reportRepository.getById(id);
    const fileBuffer = await fs.readFile(report.filePath);

    // Set custom headers
    reply.header('Content-Type', 'application/pdf');
    reply.header('Content-Disposition', `attachment; filename="${report.filename}"`);
    reply.header('Cache-Control', 'no-cache, no-store, must-revalidate');

    // Send file
    return reply.send(fileBuffer);
  }
}

// Resource definition
defineResource({
  name: 'report',
  controller: new ReportController(),
  routes: [
    {
      method: 'GET',
      path: '/:id/download',
      rawHandler: 'downloadPDF',  // ✅ Native Fastify handler, no arc pipeline
      permissions: requireAuthenticated(),
    },
  ],
});
```

### Example 2: Streaming Large Files

```typescript
import { createReadStream } from 'fs';

class VideoController {
  async streamVideo(request: FastifyRequest, reply: FastifyReply): Promise<void> {
    const { id } = request.params as { id: string };

    const video = await videoRepository.getById(id);
    const stream = createReadStream(video.filePath);

    reply.header('Content-Type', 'video/mp4');
    reply.header('Accept-Ranges', 'bytes');

    return reply.send(stream);
  }
}

// Declare via `rawHandler` on the route — no arc pipeline wrap for streaming
```

### Example 3: Custom Content-Type (CSV Export)

```typescript
class ExportController {
  async exportCSV(request: FastifyRequest, reply: FastifyReply): Promise<void> {
    const { organizationId } = request as any; // From org scope plugin

    const employees = await employeeRepository.getAll({
      filters: { organizationId },
    });

    // Convert to CSV
    const csv = convertToCSV(employees.docs);

    reply.header('Content-Type', 'text/csv; charset=utf-8');
    reply.header('Content-Disposition', 'attachment; filename="employees.csv"');

    return reply.send(csv);
  }
}

// Declare via `rawHandler` on the route — raw Fastify handler for custom content-type
```

### Example 4: Redirect

```typescript
class AuthController {
  async oauthCallback(request: FastifyRequest, reply: FastifyReply): Promise<void> {
    const { code } = request.query as { code: string };

    // Exchange code for token
    const token = await oauthService.exchangeCode(code);

    // Redirect to dashboard with token
    return reply.redirect(302, `/dashboard?token=${token}`);
  }
}

// Declare via `rawHandler` on the route — raw Fastify handler for redirects
```

### Example 5: Server-Sent Events (SSE)

```typescript
class NotificationController {
  async subscribe(request: FastifyRequest, reply: FastifyReply): Promise<void> {
    const user = (request as any).user;

    reply.raw.setHeader('Content-Type', 'text/event-stream');
    reply.raw.setHeader('Cache-Control', 'no-cache');
    reply.raw.setHeader('Connection', 'keep-alive');

    // Set up SSE stream
    const interval = setInterval(() => {
      reply.raw.write(`data: ${JSON.stringify({ time: Date.now() })}\n\n`);
    }, 1000);

    request.raw.on('close', () => {
      clearInterval(interval);
    });
  }
}

// Declare via `rawHandler` on the route — raw Fastify handler for SSE
```

## Quick Decision Guide

| Use Case | Pattern | Field |
|----------|---------|-----------|
| Standard GET/POST/PATCH/DELETE | Arc Context | `handler` |
| Business logic | Arc Context | `handler` |
| JSON responses | Arc Context | `handler` |
| File download | Native Fastify | `rawHandler` |
| File upload | Native Fastify | `rawHandler` |
| Streaming | Native Fastify | `rawHandler` |
| Custom headers | Native Fastify | `rawHandler` |
| Redirect | Native Fastify | `rawHandler` |
| SSE/WebSocket | Native Fastify | `rawHandler` |
| Custom content-type (CSV, XML, etc.) | Native Fastify | `rawHandler` |

## Common Mistakes

### ❌ Mistake 1: Putting a handler in the wrong field

The field a route fills declares its calling convention. `handler` is the arc
pipeline (one `IRequestContext`); `rawHandler` is Fastify-native
(`request, reply`, owns the response). Mixing them is a **type error** for
inline functions — but a controller-method NAME is a runtime lookup, so it is
still worth getting right:

```typescript
// IRequestContext handler → `handler`, so arc wraps it
async getConfig(req: IRequestContext): Promise<IControllerResponse> { ... }
routes: [{ handler: 'getConfig' }]

// Fastify-native handler → `rawHandler`, bypassing the pipeline
async downloadFile(req: FastifyRequest, reply: FastifyReply): Promise<void> { ... }
routes: [{ rawHandler: 'downloadFile' }]
```

Declaring BOTH fields on one route throws at boot. Before arc 2.31 this was a
`raw: boolean` flag beside a single `handler`, and both mismatches were legal
and silent.

## Accessing Fastify Features in Arc Context Pattern

**Q: What if I need to set a custom header but still want Arc's abstraction?**

**A**: You have two options:

### Option 1: Return header in metadata (if Arc supports it)

```typescript
async getConfig(req: IRequestContext): Promise<IControllerResponse> {
  return {
    success: true,
    data: config,
    meta: {
      headers: {
        'Cache-Control': 'max-age=3600',
      },
    },
  };
}
```

*Note: Check if Arc's `createFastifyHandler` supports this - it may not currently!*

### Option 2: Switch to Native Fastify pattern

```typescript
async getConfig(request: FastifyRequest, reply: FastifyReply): Promise<void> {
  const config = await configRepo.getConfig();

  reply.header('Cache-Control', 'max-age=3600');
  return reply.send({
    success: true,
    data: config,
  });
}

// Declare the route via `rawHandler`
```

## Testing

### Testing Arc Context Handlers

```typescript
import { describe, it, expect } from 'vitest';

describe('ProductController', () => {
  it('should get products by category', async () => {
    const controller = new ProductController(mockRepository);

    // Easy to test - just pass a plain object
    const result = await controller.getByCategory({
      params: { category: 'electronics' },
      query: { limit: '5' },
      body: null,
      user: null,
      headers: {},
    });

    expect(result.success).toBe(true);
    expect(result.data).toHaveLength(5);
  });
});
```

### Testing Native Fastify Handlers

```typescript
import { describe, it, expect, vi } from 'vitest';

describe('ReportController', () => {
  it('should download PDF with correct headers', async () => {
    const controller = new ReportController();

    const mockRequest = {
      params: { id: '123' },
    } as FastifyRequest;

    const mockReply = {
      header: vi.fn().mockReturnThis(),
      send: vi.fn(),
    } as any;

    await controller.downloadPDF(mockRequest, mockReply);

    expect(mockReply.header).toHaveBeenCalledWith('Content-Type', 'application/pdf');
    expect(mockReply.send).toHaveBeenCalled();
  });
});
```

## Pattern 3: Mixins vs. `routes` — which one for preset-shaped endpoints?

Arc ships four preset mixins (`SlugMixin`, `TreeMixin`, `SoftDeleteMixin`, `BulkMixin`) that auto-generate routes when the repository implements the corresponding methods (`getBySlug`, `getTree` / `getChildren`, `getDeleted` / `restore`, `bulkCreate` / etc.). You can also write the same endpoints by hand via `routes: [{ path: '/slug/:slug', rawHandler }]`.

These two paths produce the same URL from a user's perspective but look completely different in the resource file — and there's a **silent hazard** if you mix them. Pick one per endpoint.

### Decision table

| Need | Use |
|------|------|
| Slug lookup (`/slug/:slug`) on a repo with `getBySlug` | `SlugMixin` + `BaseCrudController` subclass |
| Slug lookup with custom body (joins, projections, extra auth) | `routes: [{ path: '/slug/:slug', rawHandler }]` + **delete `adapter.getBySlug`** |
| Soft-delete endpoints (`/deleted`, `/:id/restore`) | `SoftDeleteMixin` + repo implements `getDeleted` + `restore` |
| Tree traversal (`/tree`, `/:parent/children`) | `TreeMixin` + repo implements `getTree` + `getChildren` |
| Bulk create/update/delete (`/bulk`, `/bulk/delete`) | `BulkMixin` + repo implements the bulk methods |
| Any of the above with logic that doesn't fit the preset | Hand-rolled `routes: [...]`, mixin NOT composed |

### ⚠️ URL collisions silently disable mixins

If a resource declares `routes: [{ path: '/slug/:slug', ... }]` AND composes `SlugMixin`, the `routes` entry wins — Fastify mounts it first, and the mixin's auto-generated route never reaches the router. The `repo.getBySlug` method still exists, but no HTTP path invokes it: it's unreachable code living on the adapter.

This is the most common cause of "dead repository methods" in arc codebases. Before the 2.11.x decision table existed, a production refactor left ~185 LOC of `getBySlug` / `getTree` / `getChildren` boilerplate on a `createMongooseAdapter` wrapper that hadn't been exercised for weeks — the resource file used hand-rolled `routes:` entries that took precedence. After the table was added, the same refactor shrinks to ~40 LOC of genuine domain logic.

### Rule of thumb

- **Repo has the method + endpoint shape matches the mixin** → compose the mixin, delete the hand-rolled route.
- **Endpoint needs extras the mixin can't provide** (joins, projections, per-request auth) → hand-rolled route, and delete the mixin-named method from the adapter so nobody thinks it's live.

## Summary

- **Default to Arc Context Pattern** (`handler`) for 90% of your routes
- **Use Native Fastify Pattern** (`rawHandler`) only when you need:
  - File downloads/uploads
  - Streaming
  - Custom headers
  - Redirects
  - Non-JSON responses
- **For preset-shaped endpoints (slug / tree / soft-delete / bulk)**, consult the [decision table above](#pattern-3-mixins-vs-routes--which-one-for-preset-shaped-endpoints) and pick ONE path — never mix.

Both patterns work great - just pick the right one for your use case! 🚀

## Pattern 4: Write verbs — a CRUD slot backed by a domain command

Use this when the model behind a resource has a **guarded write command** — a
verb that refuses under conditions generic CRUD knows nothing about (a posted
invoice, a closed period, a locked record).

```typescript
defineResource({
  name: 'invoice',
  adapter: createMongooseAdapter({ model, repository: engine.repositories.invoices }),
  schemaOptions: {
    fieldRules: {
      status: { systemManaged: true },
      number: { systemManaged: true },
    },
  },
  writes: {
    create: (data, ctx) => engine.repositories.invoices.createDraft(data, resolveCtx(ctx.req)),
    update: (id, data, ctx) => engine.repositories.invoices.updateDraft(id, data, resolveCtx(ctx.req)),
    delete: (id, ctx) => engine.repositories.invoices.deleteDraft(id, resolveCtx(ctx.req)),
  },
})
```

Arc runs its **whole pipeline** and swaps only the persistence call:

```
sanitize (field rules) → tenant inject → actor stamp → before → around → [ YOUR VERB ] → after
                                                                            ▲
                                            repository.create() when no verb is declared
```

### Why not just override the controller method?

Because `BaseCrudController.create/update/delete` are not thin wrappers around
the repository — each one sanitizes the body against the resource's field rules,
injects the tenant field, stamps `createdBy`/`updatedBy` and runs the hook
sandwich. An override replaces all of it.

That produced a real, measured defect. A resource declaring eight
`systemManaged: true` fields overrode `update` to reach its kernel's guarded
verb. A `PATCH` on a draft then wrote `status: "posted"` and a forged document
`number` straight through, answering `200` — a document that read as posted with
no journal entry behind it. The override had been added to *close* a hole
(generic CRUD editing posted documents) and opened a wider one, because the two
safety properties had no way to coexist.

Arc warns at registration when a controller overrides a write method **and** the
resource declares field rules that the override discards.

### Return contract

A repository returns `null` for "not found"; a domain command **throws**. So
when a verb is declared:

| slot | contract |
|---|---|
| `create` | return the created document |
| `update` | a `void` return is success — arc re-reads through the repository to answer the request, rather than reporting a false 404 |
| `delete` | `undefined` is success (`deleteDraft()` returns `void`) |

### Registration-time refusals

A declared verb that can never run is decoration, so these are **errors**, not
warnings: the slot is in `disabledRoutes`, `disableDefaultRoutes: true` is set,
or the resource has no adapter repository to mount a controller against.

### `transactional: true` — running the write inside a transaction (2.33)

Wraps the **persistence step** in `withTransaction`. The verb receives the
tx-bound repository, plus `ctx.uow` — the join point for work that lives
*outside* the repository, canonically an outbox row:

```typescript
defineResource({
  name: 'order',
  adapter,
  transactional: true,
  writes: {
    create: async (data, ctx) => {
      const order = await ctx.repository.create(data);           // tx-bound
      await outbox.store(orderCreated(order), { session: ctx.uow?.session });
      return order;                                              // both commit, or neither
    },
  },
});
```

What is and isn't inside the transaction matters:

- **Hooks stay OUTSIDE the retry.** `before` / `around` already ran and must not
  re-run; `after` runs post-commit. Only the persistence step re-executes.
- **Transient conflicts re-run** the persistence step with jittered, bounded
  backoff. `VersionConflictError` is *not* transient — it surfaces as a 409, so
  a caller re-reads and re-decides rather than blindly overwriting.
- **Your verb may run more than once.** Keep it pure apart from writes through
  `ctx.repository`, which roll back with the transaction. A side effect that must
  not repeat (an email, a payment call) belongs after the commit, or in an outbox
  row written inside it.
- **Retry ownership belongs to the kit.** mongokit's driver already retries a
  conflicted transaction internally, so arc calls it exactly once; sqlitekit gets
  arc's retry loop. Arc never stacks two policies on one write.
- `ctx.uow.session` is empty on connection-bound backends (SQLite) — there the
  tx-bound repository is the only join point.

**Boot-fatal, twice over.** A repository with no `withTransaction` fails at
`defineResource()`. A repository that *has* the method but reports
`capabilities.transactions !== true` — standalone MongoDB, D1, or a topology arc
could not confirm — fails at **registration**, because `defineResource()` usually
runs at module import, before `beforeBoot()` has opened the connection. Arc will
not silently drop a transaction envelope you asked for.
