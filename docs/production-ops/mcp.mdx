# MCP (AI Agent Tools)

Expose Arc resources as [Model Context Protocol](https://modelcontextprotocol.io) tools for AI agents. The endpoint speaks MCP protocol revision **2026-07-28 only**: a fresh server per request, no sessions.

**Requires:** `@modelcontextprotocol/server`, `@modelcontextprotocol/node` and `zod` as peer dependencies (`@modelcontextprotocol/client` too, for `@classytic/arc/mcp/testing`).

```bash
npm install @modelcontextprotocol/server @modelcontextprotocol/node zod
```

## Quick Start

```typescript
import { mcpPlugin } from '@classytic/arc/mcp';

await app.register(mcpPlugin, {
  resources: [productResource, orderResource],
  auth: false,
});
```

This auto-generates up to 5 CRUD tools per resource. Tool handlers call `BaseController` — the **same pipeline as REST**, so auth, org-scoping, hooks, field permissions, and cache all apply identically.

| Tool | Input | Annotations |
|------|-------|-------------|
| `list_{plural}` | Pagination + filterable fields | read-only |
| `get_{name}` | `{ id }` | read-only |
| `create_{name}` | Required + optional fields from `fieldRules` | not destructive, not idempotent |
| `update_{name}` | `{ id }` + optional fields | destructive, idempotent |
| `delete_{name}` | `{ id }` | destructive, idempotent |

Every CRUD tool also carries `openWorldHint: false` — it reaches only the resource's own repository. Hints are always explicit, because the MCP defaults are the cautious ones (an omitted `destructiveHint` or `openWorldHint` means `true`).

Custom routes take their hints from the HTTP method: `GET` / `HEAD` / `OPTIONS` are read-only; `PUT` and `DELETE` are destructive and idempotent; `POST` and `PATCH` are destructive and not idempotent. `openWorldHint` stays unset on routes, since a handler may call anything. Set `mcp: { annotations }` on a route or action to override.

Connect an AI agent:

```bash
claude mcp add --transport http my-api http://localhost:3000/mcp
echo "List all products" | claude -p --allowedTools "mcp__my-api__*"
```

## Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `resources` | `ResourceDefinition[]` | required | Resources to expose as tools |
| `auth` | `false \| McpAuthResolver \| BetterAuthHandler` | `false` | Auth mode |
| `prefix` | `string` | `'/mcp'` | MCP endpoint path |
| `include` | `string[]` | — | Only these resources get tools |
| `exclude` | `string[]` | — | Resource names to skip |
| `toolNamePrefix` | `string` | — | Global prefix: `'crm'` → `crm_list_products` |
| `overrides` | `Record<string, McpResourceConfig>` | — | Per-resource config |
| `extraTools` | `ToolDefinition[]` | — | Custom tools alongside auto-generated |
| `extraPrompts` | `PromptDefinition[]` | — | Custom prompts |
| `instructions` | `string` | — | LLM guidance text |
| `authCacheTtlMs` | `number` | `5000` | Cache auth results for N ms; `0` disables |

## Per-Resource Overrides

```typescript
await app.register(mcpPlugin, {
  resources,
  include: ['job', 'project'],
  overrides: {
    job: {
      operations: ['list', 'get'],
      toolNamePrefix: 'db',                    // db_list_jobs, db_get_job
      names: { get: 'get_job_by_id' },         // rename specific tool
      hideFields: ['internalScore'],
      descriptions: { list: 'Browse open positions' },
    },
  },
});
```

## Auth

Three modes — you choose what fits.

### No Auth

```typescript
await app.register(mcpPlugin, { resources, auth: false });
```

### Custom Function

Return `{ userId, organizationId?, roles? }` to allow, `null` to reject:

```typescript
await app.register(mcpPlugin, {
  resources,
  auth: async (headers) => {
    if (headers['x-api-key'] !== process.env.MCP_KEY) return null;
    return { userId: 'bot', organizationId: 'org-1', roles: ['admin'] };
  },
});
```

### Better Auth OAuth 2.1

```typescript
import { mcp } from 'better-auth/plugins';

// In Better Auth config
betterAuth({ plugins: [mcp({ loginPage: '/login' })] });

// In Arc
await app.register(mcpPlugin, { resources, auth: getAuth() });
```

Auto-registers OAuth discovery endpoints (`/.well-known/oauth-authorization-server`).

## Permissions

Resource permissions work identically in REST and MCP — define once, enforced everywhere:

```typescript
import { allow } from '@classytic/arc/permissions';

defineResource({
  name: 'job',
  permissions: {
    list: (ctx) => {
      if (!ctx.user) return false;
      return allow({ policy: { orgId: ctx.user.orgId, branchId: ctx.user.branchId } });
    },
    create: (ctx) => ctx.user?.roles?.includes('admin'),
    delete: (ctx) => ctx.user?.roles?.includes('admin'),
  },
});
```

A decision's `policy` flows into `_policyFilters` → `BaseController.AccessControl` applies it to DB queries. No MCP-specific code needed.

## Multi-Tenancy

The `organizationId` from auth flows into BaseController org-scoping automatically:

```
auth returns { userId: 'alice', organizationId: 'org-a' }
  → _scope: { kind: 'member', organizationId: 'org-a' }
  → QueryResolver adds { organizationId: 'org-a' } to every query
  → Agent only sees org-a's data
```

## Custom Tools

```typescript
import { defineTool } from '@classytic/arc/mcp';
import { z } from 'zod';

const analyticsTool = defineTool('sales_report', {
  description: 'Generate sales report for a period',
  input: {
    period: z.enum(['7d', '30d', '90d']),
    region: z.string().optional(),
  },
  annotations: { readOnlyHint: true },
  handler: async ({ period, region }, ctx) => {
    const data = await analyticsService.report(period, region);
    return { content: [{ type: 'text', text: JSON.stringify(data) }] };
  },
});

await app.register(mcpPlugin, {
  resources,
  extraTools: [analyticsTool],
});
```

### Guards for Custom Tools

```typescript
import { guard, requireAuth, requireOrg, requireRole } from '@classytic/arc/mcp';

defineTool('delete_all', {
  description: 'Delete all records',
  handler: guard(requireAuth, requireOrg, requireRole('admin'), async (input, ctx) => {
    return { content: [{ type: 'text', text: 'Deleted' }] };
  }),
});
```

## AI SDK Bridge

If you already define tools with the Vercel AI SDK's `tool()` for in-process agents, expose them over MCP without duplicating the definition. The bridge handles `isAuthenticated` rejection, optional guards, `{ error }` → `isError: true` envelope translation, and thrown-error mapping.

```typescript
import { bridgeToMcp, getUserId, hasOrg, type McpBridge } from '@classytic/arc/mcp';
import { tool } from 'ai';
import { z } from 'zod';

function buildTriggerJobTool(companyId: string) {
  return tool({
    description: 'Start an investigation/fix/review job.',
    inputSchema: z.object({ phase: z.enum(['investigate', 'fix', 'review']) }),
    execute: async ({ phase }) => ({ jobId: `${companyId}-${phase}-${Date.now()}` }),
  });
}

export const triggerJobBridge: McpBridge = {
  name: 'trigger_job',
  description: 'Start an investigation/fix/review job.',
  inputSchema: { phase: z.enum(['investigate', 'fix', 'review']) },
  annotations: { destructiveHint: true },
  buildTool: (ctx) => buildTriggerJobTool(getUserId(ctx) ?? ''),
  guard: (ctx) => (hasOrg(ctx) ? null : 'Organization scope required'),
};
```

Register bridges at the plugin level, with optional per-environment filtering:

```typescript
import { buildMcpToolsFromBridges } from '@classytic/arc/mcp';

await app.register(mcpPlugin, {
  resources,
  extraTools: buildMcpToolsFromBridges(allBridges, {
    // Read-only deployment — hide destructive tools
    exclude: process.env.DEPLOYMENT === 'readonly' ? ['trigger_job'] : [],
  }),
});
```

`buildMcpToolsFromBridges` also accepts `{ include: [...] }` for strict allowlists. Bridges can be tested end-to-end with [`createTestMcpClient`](#testing).

## Custom Prompts

```typescript
import { definePrompt } from '@classytic/arc/mcp';
import { z } from 'zod';

const plannerPrompt = definePrompt('content_calendar', {
  description: 'Plan a content calendar',
  args: { platforms: z.string(), theme: z.string().optional() },
  handler: ({ platforms, theme }) => ({
    messages: [{
      role: 'user',
      content: { type: 'text', text: `Plan content for ${platforms}${theme ? ` about ${theme}` : ''}` },
    }],
  }),
});

await app.register(mcpPlugin, {
  resources,
  extraPrompts: [plannerPrompt],
});
```

## Project Structure

Custom MCP tools co-locate with their resource:

```
src/resources/
  product/
    product.resource.ts
    product.mcp.ts          ← defineTool('analyze_product', { ... })
  order/
    order.resource.ts
    order.mcp.ts            ← defineTool('fulfill_order', { ... })
```

Generate with CLI: `arc generate resource order --mcp`

## Protocol

Arc's MCP endpoint serves protocol revision **2026-07-28** and nothing older. It runs on the MCP SDK's `createMcpHandler` with `legacy: 'reject'`: every `POST /mcp` gets a fresh server, there are no sessions, and it scales horizontally and on serverless without sticky routing.

- A client must negotiate 2026-07-28 (the SDK `Client` with `versionNegotiation: { mode: 'auto' }` or `{ pin: '2026-07-28' }`).
- A 2025-era client's `initialize` is answered `400` with JSON-RPC error `-32022`, whose `data.supported` is `["2026-07-28"]`.
- `GET` and `DELETE` answer `405` with `Allow: POST`.
- Tool handlers see the caller's identity as `ctx.session` and, through the SDK's pass-through, as `ctx.extra.http.authInfo`.
- `ctx.log(level, message)` writes to the app logger (`fastify.log`), tagged with the tool name. Nothing is sent to the client: 2026-07-28 deprecates protocol logging.

```typescript
await app.register(mcpPlugin, { resources, auth: false });
```

`stateful: true` was removed with 2025-era support; passing it fails the boot. Delete `stateful`, `sessionTtlMs` and `maxSessions`.

## Health Endpoint

`GET /mcp/health` needs no MCP protocol:

```bash
curl http://localhost:3000/mcp/health
# {"status":"ok","protocolVersion":"2026-07-28","tools":10,"resources":2,"toolNames":[...]}
```

With auth configured, an unauthenticated caller gets only `status` and `protocolVersion`.

## Testing

### Unit Tests

```typescript
import { createTestMcpClient } from '@classytic/arc/mcp/testing';

const client = await createTestMcpClient({
  pluginOptions: {
    resources: [productResource],
    extraTools: [myCustomTool],
  },
  auth: { userId: 'test-user', organizationId: 'org-1' },
});

const tools = await client.listTools();
expect(tools).toHaveLength(6); // 5 CRUD + 1 custom

const result = await client.callTool('list_products', { limit: 5 });
expect(result.isError).toBeFalsy();

await client.close();
```

The client speaks 2026-07-28 and connects in memory: no port, no socket. The server side runs through the SDK's version-aware entry with 2025 serving off, so the test negotiates exactly as a production client does. To connect a server you built with `createMcpServer`, use `connectMcpTestClient(server)`, which returns `{ client, close }`. For the HTTP leg itself (status codes, headers, auth challenges), register `mcpPlugin` and use `app.inject()`.

### E2E with Claude CLI

```bash
# Start your app
npm run dev

# Add MCP server
claude mcp add --transport http my-api http://localhost:3000/mcp

# Test with auth headers via config file
cat > mcp.json << 'EOF'
{
  "mcpServers": {
    "my-api": {
      "type": "http",
      "url": "http://localhost:3000/mcp",
      "headers": { "x-api-key": "your-key" }
    }
  }
}
EOF

echo "List all products" | claude -p --mcp-config mcp.json --allowedTools "mcp__my-api__*"

# Cleanup
claude mcp remove my-api
```
