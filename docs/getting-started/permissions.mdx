# Permission System

Flexible, pluggable permission system that supports:
- Built-in role-based access control (RBAC)
- Custom permission providers (ABAC, Casbin, etc.)
- Permission helpers for common patterns
- Dynamic permissions based on data
- Multi-tenant isolation

---

## Quick Start

### Basic Permissions

```typescript
import { defineResource, allowPublic, requireAuth, requireRoles } from '@classytic/arc';

defineResource({
  name: 'post',
  permissions: {
    list: allowPublic(),                       // No auth required
    get: allowPublic(),                        // No auth required
    create: requireAuth(),                     // Any authenticated user
    update: requireRoles(['editor', 'admin']), // Specific roles
    delete: requireRoles(['admin']),           // Admins only
  },
});
```

### Ownership-Based Permissions

```typescript
import { requireOwnership, requireRoles, anyOf } from '@classytic/arc/permissions';

defineResource({
  name: 'post',
  permissions: {
    list: requireAuth(),
    create: requireAuth(),
    update: anyOf(
      requireOwnership('authorId'),  // Owner can update
      requireRoles(['admin'])        // OR admin can update
    ),
    delete: requireRoles(['admin']),
  },
});
```

## Permission Helpers

### `requireAuth()`

Require authentication (any authenticated user).

```typescript
permissions: {
  list: requireAuth(),
  get: requireAuth(),
}
```

### `requireRoles(...roles, options?)`

Require one of the specified roles. **Checks BOTH platform roles (`user.role`)
AND organization roles (`scope.orgRoles`) by default** — passing in either
layer grants access. Elevated scope always passes.

Accepts variadic strings or a single array — both forms produce identical
behavior:

```typescript
permissions: {
  create: requireRoles('admin', 'editor'),     // variadic
  update: requireRoles(['admin', 'editor']),   // array form
  delete: requireRoles('admin'),               // single role
}
```

> **Changed in 2.7.1:** `requireRoles()` now defaults to checking both
> platform AND org roles. Pre-2.7.1 it checked platform roles only and
> required `{ includeOrgRoles: true }` to also check org membership. The new
> default matches what most multi-tenant apps actually want.
>
> To restore the old platform-only behavior:
>
> ```typescript
> requireRoles(['admin'], { includeOrgRoles: false })
> ```

The `roles()` helper is now an alias of `requireRoles()` and is preserved for
backwards compatibility — for new code, prefer `requireRoles()` since it
matches the rest of the `requireXxx()` family.

### `requireOwnership(ownerField)`

Require resource ownership (user can only access their own resources). Elevated scope (`kind: 'elevated'`) bypasses ownership checks automatically.

```typescript
permissions: {
  update: requireOwnership('createdBy'),
  delete: requireOwnership('userId'),
}
```

**How it works:**
1. For `list`/`create`: Adds ownership filter automatically
2. For `get`/`update`/`delete`: Checks ownership after fetching resource
3. Returns 403 if ownership check fails
4. Elevated scope bypasses the check

### `allowPublic(options?)`

Allow public access (no authentication required).

```typescript
permissions: {
  list: allowPublic(),
  get: allowPublic(),
}
```

#### Public, but only some rows: `allowPublic({ policy })`

Most public reads should not expose every row: a storefront shows published
products, a review wall shows published reviews. Give the gate a `policy` and
everyone is still admitted, but only the rows the policy matches are readable:

```typescript
permissions: {
  list: allowPublic({ policy: { status: { $in: ['published', 'flagged'] } } }),
  get:  allowPublic({ policy: { status: { $in: ['published', 'flagged'] } } }),
}
```

The policy is enforced in the database, ANDed with whatever the caller asks
for, so `GET /reviews?status=hidden` returns nothing rather than the hidden
rows, and `GET /reviews/<hidden-id>` is a 404. It applies the same way to
aggregations and realtime feeds.

**Per caller.** Pass a function instead of an object and one gate can give
strangers, the row's author and staff a different view. Return `{}` for a caller
who should be unrestricted:

```typescript
import { allowPublic, scopeOf } from '@classytic/arc/permissions';
import { getUserId, isElevated } from '@classytic/arc/scope';

const visible = { status: { $in: ['published', 'flagged'] } };

list: allowPublic({
  policy: (ctx) => {
    const scope = scopeOf(ctx);
    if (isElevated(scope)) return {};                                        // staff: everything
    const userId = getUserId(scope);
    return userId ? { $or: [visible, { authorId: userId }] } : visible;       // author: + own
  },
}),
```

**Why not write the check by hand?** You can (`() => allow({ policy })`), but
arc treats any check as protected unless it carries the `_isPublic` flag, so a
hand-written one answers every anonymous visitor with a **401**. `allowPublic`
sets the flag for you.

**Fail-closed.** `allowPublic({ policy: {} })` throws at startup (it filters
nothing; use `allowPublic()`). A resolver that returns `undefined` or `null`
answers **403**, never an unfiltered page: return `{}` when you mean
"unrestricted".

**Inside `anyOf`**, the first branch that grants wins, and a public branch
grants everyone. So `anyOf(allowPublic({ policy }), requireRoles('admin'))`
filters admins too. Put the privileged branch first, or return `{}` for them
from the resolver.

The presets take overrides, so this also works there:
`publicRead({ list: allowPublic({ policy }), get: allowPublic({ policy }) })`.

### `denyAll(reason?)`

Deny all access (useful for disabling specific operations).

```typescript
permissions: {
  delete: denyAll('Deletion not allowed for this resource'),
}
```

## Org-Bound Helpers

Helpers that gate routes by an organization context. All read
`request.scope` set by an auth adapter (Better Auth bridge / JWT custom
auth / API-key check returning a `PermissionResult.scope`).

### `requireOrgMembership()`

Require an org-bound caller. Grants for any scope kind that carries org
context: `member`, `service` (API key), or `elevated`. Denies for `public`
and `authenticated`.

This is the canonical "is the caller acting inside an org" check, and the
usual partner for `multiTenantPreset` — any multi-tenant resource almost
always wants this gate.

```typescript
import { requireOrgMembership } from '@classytic/arc/permissions';

permissions: {
  list: requireOrgMembership(),
  get: requireOrgMembership(),
}
```

### `requireOrgRole(...roles)`

Require specific org-level role(s). Reads `scope.orgRoles` (the org-level
roles set by the BA org plugin or your JWT custom auth). ANY-match — caller
needs at least one of the listed roles. Elevated bypass.

**Service scopes (API keys) explicitly fail this check** with a guidance
reason pointing at `requireServiceScope`. Implicit "API key bypasses role
checks" is the kind of footgun that ships data breaches — services must
opt into specific scopes the same way OAuth clients do. For mixed routes,
compose with `anyOf`:

```typescript
import { anyOf, requireOrgRole, requireServiceScope } from '@classytic/arc/permissions';

permissions: {
  // Human admins OR API keys with the right OAuth scope
  create: anyOf(
    requireOrgRole('admin'),
    requireServiceScope('orders:write'),
  ),
}
```

### `requireServiceScope(...scopes)`

Require OAuth-style scope strings on a `service` (API key) identity.
Mirrors how OAuth 2.0 / Better Auth's apiKey plugin / API gateways express
machine permissions: `'orders:read'`, `'orders:write'`, `'memories:*'`.

ANY-match across the required scopes. Elevated bypass. Throws at
construction if no scopes are provided (catches typos at startup).

```typescript
import { allOf, requireOrgMembership, requireServiceScope } from '@classytic/arc/permissions';

// Variadic + array forms, both work
requireServiceScope('orders:write')
requireServiceScope('orders:read', 'orders:write')
requireServiceScope(['orders:read', 'orders:write'])

// The canonical "API key with org isolation" pattern
permissions: {
  list:   allOf(requireOrgMembership(), requireServiceScope('orders:read')),
  create: allOf(requireOrgMembership(), requireServiceScope('orders:write')),
}
```

Does NOT grant for `member` scopes — humans go through `requireOrgRole`.
For routes that should accept both, see the `anyOf` example above.

### `requireScopeContext(...)`

Require app-defined scope dimensions (branch, project, region, workspace,
…) on the current request. Reads `request.scope.context` — a
`Readonly<Record<string, string>>` slot available on member, service, and
elevated scopes. Arc takes no position on what dimensions you use; your
auth function populates `scope.context` from JWT claims, BA session
fields, or request headers.

Three call shapes:

```typescript
import { requireScopeContext } from '@classytic/arc/permissions';

// 1. Presence-only — key must exist (any value)
requireScopeContext('branchId')

// 2. Exact value match
requireScopeContext('region', 'eu')

// 3. Object form — multi-key AND semantics
requireScopeContext({ branchId: 'eng-paris', projectId: 'p-123' })

// Mixed: undefined values mean presence-only for that key
requireScopeContext({ branchId: undefined, region: 'eu' })
```

Elevated bypass. Throws at construction if no keys are provided. Pairs
with `multiTenantPreset({ tenantFields })` for row-level filtering on the
same dimensions — see the [Presets guide](./presets) for the full
multi-field config.

### `requireOrgInScope(target)`

Require that the caller's scope grants access to a target organization —
either the current org or one of its ancestors (`scope.ancestorOrgIds`).
Designed for parent-child organization hierarchies: holding company →
subsidiary → branch, MSP managing many tenant orgs, white-label parent →
child accounts.

Arc takes no position on the source of the chain — your auth function
loads `ancestorOrgIds` from your own data model. There's no automatic
inheritance: every route opts in explicitly via this helper.

Two call shapes:

```typescript
import { requireOrgInScope } from '@classytic/arc/permissions';

// Static target — rare, used when one route only ever acts on one org
requireOrgInScope('acme-holding')

// Dynamic target — extracted from request params/body/headers per call
requireOrgInScope((ctx) => ctx.request.params.orgId)
requireOrgInScope((ctx) => ctx.request.body?.organizationId)

// /orgs/:orgId/jobs — caller can act on any org in their hierarchy chain
permissions: {
  list:   requireOrgInScope((ctx) => ctx.request.params.orgId),
  create: allOf(
    requireOrgInScope((ctx) => ctx.request.body?.organizationId),
    requireOrgRole('admin'),
  ),
}
```

Elevated scope grants unconditionally. Target undefined (extractor returned
nothing) → deny with reason. Target outside chain → deny with target name
in reason.

### `requireTeamMembership()`

Require an active team in the current org. Reads `scope.teamId` (set by
the BA org plugin's teams feature, or by a custom auth function). Elevated
bypass.

```typescript
permissions: {
  // Only callers with an active team in the org
  list: allOf(requireOrgMembership(), requireTeamMembership()),
}
```

### Behavior summary

| Helper | `member` | `service` (API key) | `elevated` | Notes |
|---|---|---|---|---|
| `requireOrgMembership()` | ✅ | ✅ | ✅ | Any org-bound caller |
| `requireOrgRole(roles)` | If role matches | ❌ deny w/ guidance | ✅ bypass | Human-only by design |
| `requireServiceScope(scopes)` | ❌ | If scope matches | ✅ bypass | OAuth-style, machine-only |
| `requireScopeContext(...)` | If keys match | If keys match | ✅ bypass | App-defined dimensions |
| `requireTeamMembership()` | If `teamId` set | (n/a) | ✅ bypass | BA org plugin teams |
| `requireOrgInScope(target)` | If target in chain | If target in chain | ✅ bypass | Pure data check + elevated bypass |

## Combining Permissions

### `allOf(...checks)`

Combine multiple checks with AND logic (all must pass).

```typescript
import { allOf, requireAuth, requireRoles, requireOwnership } from '@classytic/arc/permissions';

permissions: {
  update: allOf(
    requireAuth(),                // Must be authenticated
    requireRoles(['editor']),     // AND be an editor
    requireOwnership('authorId')  // AND own the resource
  ),
}
```

### `anyOf(...checks)`

Combine checks with OR logic (any check passes).

```typescript
import { anyOf, requireRoles, requireOwnership } from '@classytic/arc/permissions';

permissions: {
  update: anyOf(
    requireRoles(['admin']),      // Admin can update anything
    requireOwnership('authorId')  // OR author can update their own
  ),
}
```

## Dynamic Permissions

### Data-Based Permissions

Check permissions based on resource data. Any `PermissionCheck` function works:

```typescript
import type { PermissionCheck } from '@classytic/arc/permissions';

permissions: {
  update: (async (context) => {
    // Only allow updates if status is 'draft'
    return context.data?.status === 'draft';
  }) as PermissionCheck,
}
```

### Complex Business Logic

```typescript
const requireQuota = (): PermissionCheck => async (context) => {
  const count = await getPublishedCount(context.user.id);
  return count < context.user.maxPosts;
};

permissions: {
  publish: allOf(
    requireRoles(['editor', 'admin']),
    requireQuota(),
  ),
}
```

## Custom Permission Patterns

Arc's permission system is function-based — any `PermissionCheck` works. For complex RBAC/ABAC, write custom permission functions.

### Using Casbin

```typescript
import type { PermissionCheck } from '@classytic/arc/permissions';
import { newEnforcer } from 'casbin';

const enforcer = await newEnforcer('model.conf', 'policy.csv');

const requireCasbinAccess = (): PermissionCheck => async (context) => {
  const allowed = await enforcer.enforce(
    context.user?.id ?? 'anonymous',
    context.resource,
    context.action
  );
  return allowed;  // a boolean is a complete answer
};

defineResource({
  name: 'document',
  permissions: {
    list: requireCasbinAccess(),
    create: requireCasbinAccess(),
    update: requireCasbinAccess(),
    delete: requireCasbinAccess(),
  },
});
```

### Custom RBAC Service

```typescript
import { allow, deny, type PermissionCheck } from '@classytic/arc/permissions';
import { rbacService } from './services/rbac';

const requireRbac = (): PermissionCheck => async (context) => {
  const { user, resource, action } = context;
  const allowed = await rbacService.can(user, action, resource);

  return allowed ? allow() : deny('Access denied by RBAC');
};

defineResource({
  name: 'invoice',
  permissions: {
    list: requireRbac(),
    create: requireRbac(),
  },
});
```

### Attribute-Based Access Control (ABAC)

```typescript
import type { PermissionCheck } from '@classytic/arc/permissions';

const requireAbac = (): PermissionCheck => async (context) => {
  const { user, data } = context;

  const rules = [
    user?.department === data?.department,
    user?.role === 'manager' && user?.region === data?.region,
    user?.role === 'admin',
  ];

  return rules.some(rule => rule === true);
};
```

## Permission Context

Every permission check receives a `PermissionContext` object:

```typescript
interface PermissionContext<TDoc = Record<string, unknown>> {
  /** Authenticated user or null if unauthenticated */
  user: UserBase | null;

  /**
   * Fastify request object. Read `request.scope` (the discriminated
   * `RequestScope` union) for org/tenant/identity context — see the
   * [Org Module guide](./presets#multitenant) for the full surface.
   */
  request: FastifyRequest;

  /** Resource being accessed (e.g., 'post', 'user') */
  resource: string;

  /** Action being performed (e.g., 'list', 'create', 'update') */
  action: string;

  /** Resource ID (for get/update/delete) — shortcut for params.id */
  resourceId?: string;

  /** All route parameters (slug, parentId, custom params, …) */
  params?: Record<string, string>;

  /** Request body data, narrowed to TDoc when the resource specifies it */
  data?: Partial<TDoc> | Record<string, unknown>;
}
```

> **Org context lives on `request.scope`, not on the context object.** All
> tenant/identity information (organizationId, teamId, orgRoles, service
> scopes, custom dimensions, ancestor orgs) is on the discriminated
> `RequestScope` union. Read it via the typed accessors from
> `@classytic/arc/scope`:
>
> ```typescript
> import { getOrgId, getOrgRoles, getServiceScopes, getScopeContext } from '@classytic/arc/scope';
>
> const orgId   = getOrgId(ctx.request.scope);                 // string | undefined
> const roles   = getOrgRoles(ctx.request.scope);              // string[]
> const scopes  = getServiceScopes(ctx.request.scope);         // readonly string[]
> const branch  = getScopeContext(ctx.request.scope, 'branchId'); // string | undefined
> ```

**Example using context:**

```typescript
import type { PermissionCheck } from '@classytic/arc/permissions';

const requireBusinessHours = (): PermissionCheck => async (context) => {
  // Access request headers
  const apiKey = context.request.headers['x-api-key'];

  // Check time-based rules
  const hour = new Date().getHours();
  const isDuringBusinessHours = hour >= 9 && hour <= 17;

  // Check IP whitelist
  const clientIp = context.request.ip;
  const isWhitelisted = await ipWhitelist.check(clientIp);

  return isDuringBusinessHours && isWhitelisted;
};
```

## Permission Results

Permission checks can return:

1. **Boolean:** Simple yes/no
```typescript
return true; // Granted
return false; // Denied
```

2. **An `AuthorizationDecision`**, built with `allow()` / `deny()`: advanced control
```typescript
import { allow, deny } from '@classytic/arc/permissions';

return allow({ policy: { organizationId: user.orgId } }); // grant + narrow rows
return deny('Access denied by policy');                   // refuse, with a reason
```

> The pre-2.30 `{ granted, filters }` object is **no longer accepted**: arc
> throws on it rather than silently reading it as a denial. Use `allow()` /
> `deny()`.

### Applying a Row Policy

A `policy` is ANDed into the query, so the caller cannot widen it with their
own filters:

```typescript
permissions: {
  list: (context) =>
    context.user
      ? allow({
          policy: {
            // User can only see their own organization's data
            organizationId: context.user.organizationId,
            // And only active records
            status: 'active',
          },
        })
      : deny('Authentication required'),
}
```

For a **public** read that narrows rows, use `allowPublic({ policy })` instead of
a hand-written check: see [`allowPublic(options?)`](#allowpublicoptions).

## Multi-Tenant Permissions

Combine permissions with multi-tenant isolation:

```typescript
import { requireAuth, requireRoles } from '@classytic/arc/permissions';

defineResource({
  name: 'invoice',
  presets: ['multiTenant'], // Auto-filter by organizationId
  organizationScoped: true,
  
  permissions: {
    list: requireAuth(),           // Any authenticated user in their org
    create: requireRoles(['admin', 'finance']), // Admins/finance in their org
    update: requireRoles(['admin', 'finance']),
    delete: requireRoles(['admin']),
  },
});
```

**Platform admin bypass:** Use the elevation plugin (`elevation` option in `createApp`) for explicit cross-org access. Elevated scope automatically bypasses org permission checks.

## Permission Functions

Arc uses **function-based permissions** for type safety and composability.

### Standard Pattern

```typescript
import { allowPublic, requireRoles, requireAuth } from '@classytic/arc/permissions';

permissions: {
  list: allowPublic(),                      // No authentication required
  get: allowPublic(),
  create: requireRoles(['admin', 'editor']), // Specific roles required
  update: requireRoles(['admin']),
  delete: requireRoles(['admin']),
}
```

### Why Functions?

1. **Type-safe** - TypeScript catches mistakes at compile time
2. **Composable** - Combine with `allOf()`, `anyOf()`
3. **Testable** - Permission logic can be unit tested
4. **Explicit** - No magic, clear intent

## Best Practices

### 1. Use Helpers for Clarity

❌ **Don't:**
```typescript
permissions: {
  update: [],
}
```

✅ **Do:**
```typescript
permissions: {
  update: allowPublic(),
}
```

### 2. Combine Permissions Logically

```typescript
permissions: {
  update: allOf(
    requireAuth(),
    anyOf(
      requireRoles(['admin']),
      requireOwnership('authorId')
    )
  ),
}
```

### 3. Document Custom Permissions

```typescript
const requireQuota = (): PermissionCheck => async (ctx) => {
  const quota = await getQuota(ctx.user.id);
  return quota.remaining > 0;
};

permissions: {
  // Only allow publishing if user has available quota
  publish: allOf(
    requireRoles(['editor']),
    requireQuota(),
  ),
}
```

### 4. Extract Custom Checks into Named Functions

For complex RBAC/ABAC logic, write reusable `PermissionCheck` functions instead of inline logic.

### 5. Test Permissions Thoroughly

```typescript
import { createTestApp } from '@classytic/arc/testing';

describe('Post permissions', () => {
  it('should deny unauthenticated users', async () => {
    const res = await app.inject({
      method: 'POST',
      url: '/posts',
      payload: { title: 'Test' },
    });
    expect(res.statusCode).toBe(401);
  });
  
  it('should allow editors to create posts', async () => {
    const res = await app.inject({
      method: 'POST',
      url: '/posts',
      headers: { Authorization: `Bearer ${editorToken}` },
      payload: { title: 'Test' },
    });
    expect(res.statusCode).toBe(201);
  });
});
```

| `requireAuth()` | Require authentication |

## Better Auth Multi-Role Support

Better Auth stores org roles as a **comma-separated string** in the `member.role` column (e.g. `"admin,recruiter"`). Arc's Better Auth adapter automatically splits this into a `string[]` and sets it on `request.scope.orgRoles`.

### How It Works

```
Better Auth DB:  member.role = "account_manager,recruiter"
                        ↓
Arc BA Adapter:  roleStr.split(',').map(r => r.trim()).filter(Boolean)
                        ↓
Request Scope:   request.scope = { kind: 'member', organizationId, orgRoles: ['account_manager', 'recruiter'] }
                        ↓
Permission Check: requireOrgRole('admin', 'recruiter')
                  → scope.orgRoles.some(r => required.includes(r))
                  → 'recruiter' matches → allow
```

### Using requireOrgRole with Multi-Role Users

`requireOrgRole()` checks if the user has **ANY** of the specified roles. This works correctly with multi-role users:

```typescript
import { requireOrgRole } from '@classytic/arc/permissions';

defineResource({
  name: 'job',
  permissions: {
    // User with roles ['account_manager', 'recruiter'] passes ALL of these:
    list: requireOrgRole('admin', 'delivery_manager', 'account_manager', 'recruiter'),
    create: requireOrgRole('admin', 'delivery_manager'),  // fails — no admin or DM
    delete: requireOrgRole('admin'),                       // fails — no admin
  },
});
```

### Multi-Role with createOrgPermissions

`createOrgPermissions()` takes the **union** of all role permissions when a user has multiple roles:

```typescript
const perms = createOrgPermissions({
  statements: {
    job: ['create', 'update', 'delete', 'assign'],
    candidate: ['create', 'update', 'delete'],
  },
  roles: {
    admin: { job: ['create', 'update', 'delete', 'assign'], candidate: ['create', 'update', 'delete'] },
    delivery_manager: { job: ['create', 'update', 'assign'], candidate: [] },
    account_manager: { job: ['assign'], candidate: ['create', 'update'] },
    recruiter: { job: [], candidate: ['create', 'update'] },
  },
});

// User with roles: ['account_manager', 'recruiter']
// Effective permissions (union):
//   job: ['assign'] (from account_manager)
//   candidate: ['create', 'update'] (from both)
```

### Custom Scoped Permissions with Filters

#### Multiple teams, workspaces, or host-defined tenancy names

Keep one **active selection per request**. A user may belong to many teams or
workspaces in the host database, but the authenticated `RequestScope` should
carry only the team/workspace selected for this operation. The auth resolver
must verify that selection against the user's memberships before constructing
the scope. This prevents an accidental union of every tenant the user can
access from widening a query.

Arc's built-in `teamId` is optional convenience, not a required naming model.
Hosts can use any dimension through `scope.context`, gate it with
`requireScopeContext`, and apply it as a repository filter with
`multiTenantPreset({ tenantFields })`:

```typescript
// In the host's authentication/membership resolver, after verifying access:
request.scope = {
  kind: 'member',
  userId: user.id,
  userRoles: user.roles,
  organizationId: membership.organizationId,
  orgRoles: membership.roles,
  context: { workspaceId: selectedWorkspace.id },
};

const workspacePermission = allOf(
  requireOrgMembership(),
  requireScopeContext('workspaceId'),
);

const workspaceTenant = multiTenantPreset({
  tenantFields: [
    { field: 'organizationId', type: 'org' },
    { field: 'workspaceId', contextKey: 'workspaceId' },
  ],
});
```

When membership rules require database lookups, hosts may pass any custom
`PermissionCheck` function. Return `allow({ policy })` to narrow rows,
or return a verified `scope` from an earlier authentication permission. Built-in
role checks remain preferable when no custom lookup or row filter is needed.

For permissions that need query scoping (e.g. "AM sees only assigned jobs"), write a custom `PermissionCheck` that reads org roles from `request.scope`:

```typescript
import { allow, deny, scopeOf, type PermissionCheck } from '@classytic/arc/permissions';
import { isElevated, getOrgRoles } from '@classytic/arc/scope';

export function canAccessJobs(): PermissionCheck {
  return (ctx) => {
    const scope = scopeOf(ctx);
    if (isElevated(scope)) return allow();

    const orgRoles = getOrgRoles(scope);
    if (orgRoles.length === 0) return deny('Not an org member');

    // Admin/DM see everything
    if (orgRoles.some(r => ['admin', 'delivery_manager'].includes(r))) {
      return allow();
    }

    const userId = ctx.user?.id;
    const isAM = orgRoles.includes('account_manager');
    const isRecruiter = orgRoles.includes('recruiter');

    // Multi-role: union both assignment filters
    if (isAM && isRecruiter) {
      return allow({ policy: { $or: [{ assignedAMs: userId }, { assignedRecruiters: userId }] } });
    }
    if (isAM) return allow({ policy: { assignedAMs: userId } });
    if (isRecruiter) return allow({ policy: { assignedRecruiters: userId } });

    return deny('Insufficient role');
  };
}
```

### Best Practice: Use requireOrgRole When Possible

Prefer Arc's built-in `requireOrgRole()` over custom role checks. Only write custom `PermissionCheck` functions when you need a row `policy` for query scoping (and for a public read, reach for `allowPublic({ policy })` first).

| Use Case | Approach |
|----------|----------|
| Simple role gate (admin can delete) | `requireOrgRole('admin')` |
| Multiple allowed roles | `requireOrgRole('admin', 'editor', 'manager')` |
| Role-based query scoping | Custom `PermissionCheck` with `filters` |
| Resource:action RBAC | `createOrgPermissions({ roles, statements })` |
